# المرحلة 10 — وكيل أليسوم التنفيذي (ALYSSUM AI AGENT CORE)

> معاينة معزولة على الفرع التجريبي فقط. لا دمج في `main`، لا تعديل `VERSION`، لا نشر Worker، لا تعديل واجهات إنتاج أو مخططات قواعد البيانات. كل العمل داخل `admin-preview/spatial-os/`.

## 1) ما الذي صار «اسألني»؟
في الوضع الحقيقي (جلسة مدير/موظف على متجر حقيقي) لوح «اسألني» المركزي (زر النواة) لم يعد إطاراً لصفحة المساعدة بل **وكيلاً تنفيذياً أصلياً**: يفهم تعليمة بالدارجة الجزائرية/الفصحى/الفرنسية، يختار **أداة حقيقية مخوَّلة**، ينفّذها على الـAPI الفعلي، يتفاعل مع الألواح الفضائية الموجودة، ثم **يبلّغ بنتيجة متحقَّقة من الخادم** (أو بخطأ دقيق). لوح «اسألني» القديم (قاعدة المعرفة) باقٍ كمرجع إضافي بزر «دليل» (`help`)، وفي الوضع التجريبي بلا خادم تبقى المحاكاة القديمة كما هي.

```
   إدخال (لوحة مفاتيح/صوت)                                   ┌──────── لوح الطلبات (iframe admin.html) ─────────┐
        │                                                    │ مرشّحات حقيقية، معاينة الطلب، Admin.confirmOrder │
        ▼                                                    └───────▲──────────────────────────┬──────────────┘
  ┌─ ui.js ──────────┐   submit(نص)   ┌──────── core.js ─────────┐    │ SpatialOS.open + eval     │ order_update (fetch)
  │ حالات/خط زمني/   │ ─────────────▶ │ Context · Authorization  │    │ (نفس الأصل)               ▼
  │ بطاقة موافقة     │ ◀── أحداث ──── │ Orchestrator · Confirm   │ ───┘                     جسر الحدث (bridge.js)
  └──────────────────┘                │ Verifier · Audit         │                              │ حدث مُنمَّط بعد نجاح الخادم
                                      └────┬───────────┬─────────┘                              ▼
                              nlu.js ◀─────┘           └───▶ tools.js (سجل أدوات + مخططات)   Event Hub (hub.js)  ──▶ تحديث موجَّه للألواح
                              (فهم)                         │ GET/POST api/index.php (جلسة المستخدم) ▲
                                                            └────────────────────────────────────────┘ expect / settle / refreshNow / registerAgent
```

## 2) المكوّنات (ملفات جديدة في `agent/`)
| المكوّن | الملف | المسؤولية |
|---|---|---|
| NLU | `nlu.js` | فهم حتمي (بلا نموذج لغوي) للدارجة/الفصحى/الفرنسية: نية + معطيات + لغة + ثقة؛ متابعات سياقية («وكم عددهم؟»، «وفي وهران؟»، «أكد هذا الطلب»، «والثاني؟»)، تعامل مع الأرقام الترتيبية والأسماء والمنتجات الحقيقية (تطابق تقريبي مع رفض الغموض) |
| Tool Registry | `tools.js` | تعريف كل أداة: اسم، مخطط معطيات (`additionalProperties:false`، enum، أنماط، حدود)، صلاحيات، خطورة (`read`/`ui`/`write`)، نقطة النهاية الحقيقية؛ عميل خادم بمهلة وتصنيف أخطاء |
| Context Manager | `core.js` | آخر نية/قائمة طلبات/طلب مُركَّز/منتج/انتظار توضيح؛ يُصفَّر عند تغيّر المستخدم |
| Authorization Manager | `core.js` | الهوية والصلاحيات من `GET me` فقط (الجلسة)؛ إعادة جلب طازجة قبل أي كتابة؛ أدوات المالك فقط (`owner`) |
| Execution Orchestrator | `core.js` | نية → خطوات أدوات مرئية، تحقق مخطط، مهلة، خطأ مصنَّف، مخطِّط LLM اختياري مقيّد |
| Confirmation Manager | `core.js` | رمز موافقة عشوائي **لمرة واحدة** مرتبط بأداة+معطيات+طلب محدد، مهلة 90ث، يُلغى برسالة أخرى؛ الموافقة تُقبل فقط عبر **قدرة واجهة الوكيل** (`registerUI()` تُمنح لأول مستدعٍ فقط) |
| Result Verifier | `tools.js`/`core.js` | لا نجاح بلا قراءة حالة الخادم؛ ثم تأكيد وصول الحدث للمركز وانتهاء مزامنة الألواح؛ وإلا تقرير صريح بما لم يتحقق |
| Event Hub Adapter | `tools.js`/`hub.js` | `SpatialHub.expect/settle/refreshNow/registerAgent().publish` — نفس المركز (لا نظام أحداث موازٍ) |
| Audit & Error Handler | `core.js` | سجل تدقيق (نية، أدوات، طلب/موافقة/رفض/انتهاء) **بلا هواتف ولا أسماء ولا أسرار**؛ أخطاء بعبارات دقيقة |
| UI | `ui.js` + `agent.css` | كرة مركزية بحالات (idle/listening/thinking/executing/speaking/awaiting/success/error) تنعكس على زر النواة، خط زمني: «فهمت ← الأداة ← الحالة ← النتيجة»، وسوم «حقيقة/تقدير/توصية»، بطاقة موافقة بعدّاد، ميكروفون/قراءة صوتية اختيارية، نصوص بـ`textContent` فقط |

## 3) سجل الأدوات الفعلي والـAPI المستعمل
| الأداة | الخطورة | الصلاحية | نقطة النهاية الحقيقية |
|---|---|---|---|
| `orders.list` | قراءة | `orders` | `GET api/index.php?r=orders` ثم تصفية (حالة/ولاية/بحث/فترة) |
| `orders.get` | قراءة | `orders` (+`customers` لرؤية الهاتف كاملاً وإلا مقنَّع) | `GET r=orders` |
| `sales.summary` | قراءة | `orders` | `GET r=orders` (المبيعات غير الملغاة بتعريف اللوحة؛ «تقدير» منفصل ومُعلَّم) |
| `sales.top_product` | قراءة | `orders` | `GET r=orders` (تجميع بنود الطلبات) |
| `products.search` / `products.get` | قراءة | مالك | `GET r=file&path=assets/js/data.js` |
| `inventory.read` | قراءة | مالك | `GET r=file` (`data.js` + `assets/data/inventory.json`) |
| `customers.find` | قراءة | `customers` | `GET r=orders` |
| `settings.read` | قراءة | مالك | `GET r=kv&k=guard` / `k=stockcfg` (قراءة فقط، مفاتيح مسموحة محدودة) |
| `ui.open_panel` / `ui.filter_orders` / `ui.show_order` / `ui.current_order` / `analytics.refresh` | واجهة | `orders` للمرتبط بالطلبات | `SpatialOS.open` + مرشّحات `admin.html` نفسها (`#order-filter-*`, `Admin.applyOrderFilters`, `Admin.openOrderPreview`) |
| **`orders.confirm`** | **كتابة** | `orders` + `orders.write` | `POST r=order_update {id,status:"confirmee"}` **عبر `Admin.confirmOrder` لوح الطلبات نفسه** (حركة المخزون والإشعارات كما هي) |

الكتابة الوحيدة هي تأكيد طلب في انتظار التأكيد. **لا إلغاء/حذف/تعديل بيانات/إرسال لشركة توصيل/دفع.**

## 4) سيناريو القبول (يُختبر بالكامل بلا محاكاة أي مكوّن)
«وريني الطلبات غير المؤكدة» → الوكيل يقرأ الطلبات (`orders.list`) ويفتح لوح الطلبات الحقيقي مفلتراً (`ui.filter_orders`، ويقارن صفوفه بالخادم) → المستخدم ينقر معاينة طلب → «أكد هذا الطلب» → الوكيل يحدّد الطلب بالضبط من معاينة اللوح ويتحقق منه من الخادم ويفحص المخاطر (إرسال تلقائي/مخزون) ثم **يطلب موافقة صريحة** (بطاقة) دون أي كتابة → نقرة «موافقة» → الكتابة عبر منطق اللوح → قراءة الخادم تؤكد `confirmee` → حدث `order.confirmed` يصدر من جسر اللوح **بعد** نجاح الخادم (أو يُنشره الوكيل عبر المركز احتياطاً إن ضاع) → تحديث موجَّه للألواح المرتبطة بلا إعادة تحميل → الوكيل يروي النتيجة الفعلية.

## 5) الأمان
- **الصلاحية من الخادم فقط**: لا هوية ولا مستأجر ولا صلاحية تأتي من النموذج أو الإطار أو رسائل `postMessage`؛ كل الطلبات same-origin بجلسة المستخدم، والخادم يرفض ما لا يُخوَّل (403 ← رسالة «ليست لديك صلاحية…»). فحص الصلاحية في الوكيل لتجربة المستخدم فقط.
- **الكتابة**: موافقة صريحة، رمز لمرة واحدة (مهلة 90ث)، إعادة تحقق (حالة الطلب/الصلاحية/المخاطر) قبل التنفيذ، رفض آلي إن كان التأكيد سيُطلق إرسالاً تلقائياً لشركة توصيل أو المخزون لا يكفي.
- **لا نجاح قبل الخادم**: التقرير يبنى من قراءة الخادم؛ عند فشل الكتابة يعاد اللوح لحقيقة الخادم ولا يُنشر أي حدث.
- **PII**: الهاتف مقنَّع لمن لا يملك «العملاء»؛ سجل التدقيق بلا هواتف/أسماء؛ نص الزبون يُعرض نصاً (لا HTML).
- **مخطِّط LLM اختياري** (`setPlanner`): خرجه يمر على نفس مدقّق المخطط ولا يُسمح له إلا بأدوات القراءة. **لم يُوصَل بمزوّد حقيقي ولم يُختبر إلا بدالة تجريبية.**

## 6) تعديلات على ما سبق (متوافقة للخلف)
- `hub.js`: إضافة `expect`, `onAccepted`, `refreshNow`, `settle`, `registerAgent` (الأخيرة مرة واحدة)، ومراقبون يُخطَرون عند قبول حدث؛ الواجهة ما زالت مجمَّدة والإصدار 1 وكل دوال المرحلة 9 كما هي (اختبارات المرحلة 9 كاملة تمر).
- `spatial.js`/`panels.js`: لوح `ai` صار أصلياً في الوضع الحقيقي (إطار «اسألني» القديم صار اللوح المخفي `help`)؛ `phase8.js` حُدِّث تبعاً لذلك.
- لا تعديل في `bridge.js` ولا أي ملف خارج `admin-preview/spatial-os/`.

## 8) حدود معروفة — ما لا يدّعيه هذا التسليم
- **أحداث خارجية/Webhook** (طلب جديد من الزبائن، تتبّع شركة التوصيل، موظف آخر على جهاز آخر…) **لا تصل لحظياً** إلى الألواح؛ المزامنة اللحظية هنا تغطي كتابات اللوحات داخل نفس الجلسة والوكيل فقط، والباقي يعتمد على التحديث الدوري/التحقق عند التفعيل المبنيين في المرحلة 9 — **ليست مزامنة لحظية كاملة**.
- **حدّ الثقة نفس الأصل**: الألواح الحقيقية iframe من نفس الأصل، فشيفرة الصفحة نفسها قادرة نظرياً على الوصول إلى `window.parent`؛ الحماية هنا أن الموافقة تتطلب قدرة تُمنح لواجهة الوكيل وحدها ورمزاً عشوائياً، وأن الخادم هو من يفرض الصلاحية. لا تُعدّ رسائل `postMessage` وسيلة مصادقة أبداً. جهة خبيثة تنفّذ شيفرة داخل الأصل نفسه (XSS في اللوحة) تتجاوز هذا الحدّ — الدفاع عنه خارج نطاق هذه المرحلة.
- **الفهم حتمي**: يغطي صيغ الدارجة/الفصحى/الفرنسية المختبرة؛ صيغ أبعد قد تُرفض برد إرشادي («لم أفهم»). لا نموذج لغوي موصول.
- **الصوت**: الميكروفون (`SpeechRecognition`) والقراءة (`speechSynthesis`) مكتوبان ويعتمدان على المتصفح؛ **لم يُختبرا بميكروفون/مكبّر حقيقيين** (حالتا listening/speaking غير مُختبرتين).
- **كتابة واحدة**: تأكيد طلب فقط؛ إلغاء/تعديل/شحن/مخزون/أسعار غير مدعومة عمداً (تتطلب سياسات موافقة وتدقيقاً أوسع).
- **تأكيد الطلب يُحجَب** إن كان سيُطلق إرسالاً تلقائياً لشركة توصيل أو المخزون لا يكفي (يُنفَّذ يدوياً من اللوح). متجر الاختبار بلا شركة توصيل مفعّلة، فمسار «الحجب بسبب الإرسال التلقائي» مكتوب لكن **لم يُختبر ضد شركة حقيقية** (ولا يُرسَل طرد حقيقي ياليدين أبداً).
- **جسر اللوح يتجاهل أحداث الكتابة لنحو 0.8ث بعد تحديث** (منع الحلقات)؛ الوكيل ينتظر ذلك قبل الكتابة، وإن ضاع الحدث رغم ذلك ينشره عبر المركز **بعد** تأكيد الخادم ويصرّح بذلك في تقريره.
- الأداء قيس بمتصفح Chromium برسم برمجي (بلا GPU)؛ أرقام الأجهزة الحقيقية ستختلف.
- لم يُجرَّب مع متجر منتجاته بآلاف الطلبات (الحدّ الأقصى للخادم 2000 طلب في الاستجابة).
