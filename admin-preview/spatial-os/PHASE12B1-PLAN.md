## 2) عقد النتيجة الموحّد (`API.submitOrderTruth`)
الحالات: `CONFIRMED` · `DUPLICATE_CONFIRMED` · `REJECTED` · `UNKNOWN` · `SERVER_ERROR` · `INVALID_RESPONSE`. النتيجة: `{ state, ok, id, error, status, retryable, key, backend }` حيث **`ok` صحيحة فقط للحالتين الأوليين**.
قواعد التصنيف (بالترتيب، لكل خلفية):
1. استثناء شبكة/مهلة ← `UNKNOWN` (retryable، بنفس المفتاح).
2. نص ردّ فارغ/JSON تالف: إن كانت الحالة 2xx ← `INVALID_RESPONSE`؛ وإلا حسب فئة الحالة.
3. 2xx: يشترط `ok === true` + `id` نصّ صالح الصيغة (يُرفض الفارغ/المشوَّه/المحلي) ⇒ `CONFIRMED`، ومع `duplicate:true` ⇒ `DUPLICATE_CONFIRMED`؛ `ok:false` مع `error` ⇒ `REJECTED`، وبلا `error` ⇒ `INVALID_RESPONSE`؛ كل ما عدا ذلك `INVALID_RESPONSE`.
4. 4xx (400/401/403/409/422/429) ⇒ `REJECTED` (429/409 تحمل `retryable` مناسبة؛ لا تصير نجاحاً أبداً).
5. 5xx ⇒ `SERVER_ERROR` (503 busy/try_again retryable بنفس المفتاح).
6. خلفية Google Sheets (no-cors) ⇒ `UNKNOWN` دائماً مع `error:"unverifiable_backend"` (لا تأكيد ممكن).
7. عشوائية آمنة غير متاحة ⇒ **لا إرسال** (`REJECTED` محلي `secure_random_unavailable`).
واتساب لا يغيّر الحالة أبداً؛ والمعرّف لا يُولَّد في العميل.

## 3) مفتاح idempotency وبصمة الطلب
- **البصمة القانونية:** تسلسل JSON ثابت الترتيب لحقول: الاسم (تنظيف مسافات) والهاتف (أرقام فقط، 00213/213→0) والولاية والبلدية ونوع التوصيل والمكتب وبنود (slug+title[يحمل التنويع]+qty+price) **مرتّبة** والمجاميع (subtotal/fee/discount/total) والكوبون والترويج و`extra` كاملاً عدا المفاتيح المتقلبة (`🔗 مرجع`). حقول مكافحة الروبوت (`hp`,`ftok`) و`ctoken` والملاحظات خارجها.
- **التجزئة:** SHA-256 كاملة (WebCrypto، وبديل SHA-256 نقي عند غياب `crypto.subtle`) بملح عشوائي لكل تبويب؛ **لا تجزئة قصيرة**، ولا PII خام في التخزين.
- **المفتاح:** `crypto.randomUUID()` أو `getRandomValues` (32 hex)؛ **لا `Math.random`**؛ تعذّر العشوائية ← فشل آمن بلا إرسال.
- **دورة الحياة:** يُولَّد عند أول محاولة لبصمة جديدة؛ يُعاد استعماله لكل إعادة لنفس البصمة (ضمنها عدم اليقين/5xx/الشبكة)؛ تغيّر أي حقل تجاري ← بصمة جديدة ← مفتاح جديد؛ يُمسح عند `CONFIRMED`/`DUPLICATE_CONFIRMED`/`REJECTED`؛ يُحفظ عند `UNKNOWN`/`SERVER_ERROR`/`INVALID_RESPONSE`؛ **TTL 30 دقيقة** في العميل (يُنظَّف عند التحميل)، واحتفاظ الخادم 7 أيام (تنظيف تلقائي). التخزين `sessionStorage` (لكل تبويب؛ تبويبان/زبونان لا يتشاركان مفتاحاً).
- **الخادم (PHP):** بصمة الخادم تُوسَّع لتغطي discount وعناوين البنود (التنويع) و`extra` القانوني؛ نفس المفتاح بمحتوى مختلف ← 409 صريح؛ السجل في نفس معاملة الطلب (قائم)؛ التحقق قبل كشف الطلب الأصلي يتطلب نفس البصمة (محتوى الزبون)؛ تنظيف سجلات أقدم من 7 أيام.
- **Supabase:** إضافة `order_idem` ومعالجة `p.idem` داخل `submit_order` (ذرّية بطبيعة الدالة) + معرّف أطول مع إعادة محاولة تصادم (مماثل لـPHP) — **في ملف SQL فقط (لا يُطبَّق على الإنتاج)**؛ يُختبر على PostgreSQL محلي بهيكل Supabase مبنيّ يدوياً ⇒ الحالة القصوى **PARTIAL**.
- **Worker:** `ref` فريد (مُختبَر) — يُوثَّق كمرآة/خلفية API؛ لا مسار تسجيل للمتجر عبره إلا `hold` (يُحكَم `ok`).

## 4) واجهة الزبون (كل المسارات)
`CONFIRMED`: «تم تسجيل طلبك» + **رقم الطلب من الخادم**. `DUPLICATE_CONFIRMED`: نفس الشيء مع «سبق تسجيله». `REJECTED`: سبب الرفض (من رمز الخادم) بلا إعادة تلقائية. `UNKNOWN`: «تعذّر الحصول على تأكيد تسجيل طلبك — قد يكون وصلنا؛ **لا تُرسل طلباً جديداً**؛ أعد المحاولة (نفس الطلب)» + زر إعادة بنفس المفتاح + رابط واتساب منفصل موسوم «رسالة فقط — لا يُسجّل طلبك». `SERVER_ERROR`/`INVALID_RESPONSE`: رسالة عطل مؤقت + إعادة. **بيانات النموذج تبقى** في كل حالة غير ناجحة. واتساب التلقائي يُفتح **بعد التأكيد فقط**. أحداث البكسل/كوبونات «مستعملة» وعلامة الحارس المحلي لا تُسجَّل إلا بعد التأكيد.
