## WS1 — اختفاء تصادم معرّف الطلب
**الحالة الراهنة (من الكود):** `id = S|M + yymmdd + '-' + 5 hex` (`index.php:559`)، `PRIMARY KEY` على `orders.id`، **لا معالجة لمخالفة التفرّد** (PDOException ← HTTP 500)، **لا معاملة**: الكود يستهلك كود التخفيض (`UPDATE promo_codes SET used_order=$id`) **قبل** `INSERT`؛ فإذا فشل الإدراج يبقى الكود «مستهلكاً» بطلب غير موجود. لا مفتاح idempotency، وحارس `dup` يرفض إعادة الإرسال المشروعة (409). المخزون لا يُحجز في الخادم (وسم 📦 يُكتب عند التأكيد من اللوحة)، والإشعارات لا تُرسل من هذا المسار.
**التصميم:**
1. معرّف عام بنفس الشكل `S|M yymmdd-XXXXXXXX` لكن **8 رموز hex مبدئياً** (32 بتاً)، تتوسّع (10 ثم 12) عند التصادم؛ `random_bytes`. الشكل القديم (5) يبقى مقروءاً؛ تُوسَّع تعابير التحليل في الوكيل من `{4,6}` إلى `{4,14}`.
2. إنفاذ التفرّد في قاعدة البيانات (قائم: PK) + **التقاط صريح** لمخالفة `orders.id` فقط (`UNIQUE constraint failed: orders.id`) وإعادة محاولة محدودة (5)، وأي خطأ آخر لا يُعاد كأنه تصادم؛ استنفاد المحاولات ← `503 try_again`.
3. **معاملة واحدة** (`BEGIN IMMEDIATE`): استهلاك كود التخفيض + إدراج الطلب + ملاحظة الطلب اليدوي + سجل idempotency + (تدقيق) — إما كلها أو لا شيء. `SQLITE_BUSY` ← `503 busy` + `Retry-After` لا تصادماً.
4. **Idempotency:** مفتاح `Idempotency-Key` (أو `order.idem`) بطول/شكل محدّدين؛ جدول إضافي `order_idem(key PK, order_id, req_hash, created_at)` يُنشأ تلقائياً (نمط `CREATE TABLE IF NOT EXISTS` المتّبع)؛ نفس المفتاح ونفس المحتوى ← يعيد الطلب الأول (`duplicate:true`) **قبل** الحراس (فلا 409/429 خاطئان على إعادة شبكة)؛ نفس المفتاح بمحتوى مختلف ← `409 idempotency_key_reuse`؛ مفتاح جديد = طلب جديد مشروع. لا مرشّح زمني.
5. واجهة المتجر ترسل المفتاح (يُولَّد مرة لكل محاولة إتمام ويُعاد عند إعادة الإرسال).
6. خطّاف اختبار وحيد: `ALYSSUM_TEST_MODE=1` فقط يسمح بـ`ALYSSUM_TEST_FORCE_IDS` لإجبار التصادم؛ لا أثر بدونه.
**الاختبارات المطلوبة (`test/phase12b-orders.js`):** 10,000 تسلسلياً؛ ≥1,000 متزامنة (`PHP_CLI_SERVER_WORKERS`)؛ تصادم قسري؛ فشل قاعدة بيانات قسري (TRIGGER)؛ تكرار idempotency؛ محاكاة إعادة شبكة؛ اتساق كود التخفيض/الجداول بعد الفشل؛ قراءة معرّفات قديمة. **القبول:** 0 معرّف مكرّر، 0 طلب مقبول ضائع، 0 طلب مكرّر لمفتاح، 0 أثر جانبي بعد فشل، رموز HTTP صحيحة، توافق خلفي.

## WS2 — اكتمال بيانات الطلبات والتجميع
**العقد الحالي (يوثَّق قبل التغيير):** `GET orders` ← `{ok, orders:[…≤2000]}` مرتبة تنازلياً بـ`created_at`، حقول `id,date,name,phone,wilaya,commune,dtype,desk,items,subtotal,fee,total,coupon,discount,extra,status,note`. المستهلكون: `admin.html` (4 مواضع: الرئيسية، التحليلات، البحث، الفلاتر… كلها تحسب في المتصفح)، `assets/js/api.js` (ويكرّر `limit=2000` في مسار Supabase)، وكيل Spatial OS (`tools.js`)، تقارير/تصدير في اللوحة.
**التصميم (إضافي فقط، بلا كسر):**
1. `GET orders` يبقى كما هو ويضيف حقولاً: `total_count`, `returned`, `truncated`, `window`, `has_more`, `next_cursor`.
2. `orders_page`: ترقيم بمؤشر `(created_at,id)` (ترتيب ثابت، لا تكرار ولا فقد عند ورود طلبات جديدة)، `limit` ≤ 500، فلاتر (`status,since,until,q,wilaya`) محفوظة عبر الصفحات، `total` صريح، `has_more`.
3. `orders_stats`: تجميع على الخادم (أعداد الحالات، الإيراد غير الملغى، سلسلة الأيام، أفضل المنتجات) لأي نطاق زمني — صحيح مهما كان الحجم.
4. الوكيل: `sales.summary` و`sales.top_product` وعدّاد الجديد من `orders_stats`؛ `orders.list` من `orders_page`؛ رجوع آمن للمسار القديم مع الإفصاح عند غياب النقاط (متاجر أقدم).
5. لوحة التاجر: لافتة صريحة عند `truncated` + استعمال `orders_stats` لأرقام الرأس حيث أمكن؛ ما لا يتغطى يُسجَّل **PARTIAL** لا يُخفى.
**الاختبارات:** 100/1,000/10,000/50,000 طلب؛ تطابق الأعداد/المبالغ مع SQL مباشر؛ ترقيم بلا تكرار/فقد أثناء إدراج متزامن؛ فلاتر عبر الصفحات؛ توافق عميل قديم.

## WS3 — عزل المستأجرين (هجومي)
- **اكتُشف قبل الكتابة (تجربة حقيقية):** كوكي جلسة مدير متجر A **قُبلت في متجر B** على نفس الخادم (200 وبيانات B) لأن `session_save_path` مشترك والجلسة بلا ربط بالتثبيت. هذا فشل عزل حرج في نسخة الاستضافة؛ يُصلَح: (أ) مسار جلسات خاص بكل تثبيت `api/_data/sessions` (0700) مع GC صريح؛ (ب) ختم تثبيت `inst` (HMAC سرّ التثبيت) يُفحص عند كل طلب في `index.php` و`update.php` و`llm.php`؛ جلسات قديمة تُبطَل (إعادة دخول واحدة، موثَّق).
- اختبارات PHP: جلسات عبر متجرين (مدير، موظف)، معرّفات طلبات/عملاء عبر المتاجر، `update.php`، `llm.php`.
- Worker (`platform/api`): تشغيل `isolation` و`isolation-fuzz` القائمين + هجمات إضافية (مفتاح مستأجر A ضد معرّفات B، idempotency/`ref` عبر مستأجرين، ترقيم/`after` عبر مستأجرين، أحداث).
- Supabase RLS: يحتاج Postgres محلياً؛ إن تعذّر التثبيت ← **BLOCKED** (لا محاكاة).
- لا يُختبر شيء على مشروع Supabase الإنتاجي.

## WS4 — ألواح Spatial OS المخفية/المصغّرة
**الوضع الحالي:** `hub.setVisible` يوقف المزامنة للألواح الخفية، لكن iframes (`admin.html` ≈25k عقدة/لوح) تبقى حيّة (مؤقتات، تحديث دوري، رسم).
**التصميم:** تجميد آمن للوح المصغّر/المخفي: (أ) `visibility:hidden` + `content-visibility` لإيقاف الرسم، (ب) رسالة `suspend` عبر الجسر توقف مؤقتات اللوحة، (ج) عند الاستئناف `resume` + مصالحة Hub (`refreshNow`) — حالة اللوح (الجدول/التمرير/الفلاتر) محفوظة لأن الـiframe لا يُدمَّر؛ خيار ثانٍ أعمق (تفريغ DOM مع الاستعادة من لقطة الحالة القائمة) يُدرس فقط إن لم يكفِ.
**القياس قبل/بعد:** CPU وheap وعقد DOM ومهام طويلة مع 4 ألواح (2 مصغّرة)، ودقة الحالة بعد الاستئناف (لا فقد فلاتر/تمرير/تحديد)، ومزامنة Hub.
