## 3) نتيجة كل Workstream

### A — عقد Supabase
**العقد الموثَّق (مستقل عن PHP)** — في التعليق أعلى `classifySb` داخل `api.js` وهنا:

| العنصر | العقد |
|---|---|
| الاستدعاء | `POST /rest/v1/rpc/submit_order` بجسم `{p:{…الطلب…, idem}}` |
| ردّ النجاح | HTTP 200 + جسم JSON **نصّي فقط** هو معرّف الطلب (مثل `"S261113-3D323D5C"`). لا `ok` ولا `duplicate` |
| تكرار بنفس المفتاح | تعيد الدالة معرّف الطلب الأصلي نفسه (⇒ `CONFIRMED` بالمعرّف الأصلي؛ العميل لا يميّز «تكراراً» هنا) |
| تعارض المفتاح | استثناء `idempotency_key_reuse` ← HTTP 400 `{code:"P0001",message:…}` ← `REJECTED` |
| أخطاء التحقق | 400 + `message` = الرمز (`invalid_phone`…) ← `REJECTED` |
| `try_again` | 400 لكن عطل مؤقت ← `SERVER_ERROR` قابل للإعادة |
| 401/403/409/422/429 | `REJECTED` (لا تُعاد تلقائياً إلا 429/408 كـ`retryable`) |
| 5xx | `SERVER_ERROR` |
| معرّف الطلب | يولّده **الخادم** (دالة SQL) بـ8 hex (يكبر عند التصادم) |

**شروط قبول النجاح (كلها مطلوبة):** 2xx؛ ردّ ليس من إعادة توجيه وعنوانه ينتهي بـ`/rest/v1/rpc/submit_order`؛ جسم JSON نصّي؛ معرّف مطابق للصيغة المعتمدة. كائن/مصفوفة/رقم/`null`/صف جدول/فارغ/مشوَّه ← `INVALID_RESPONSE`.

**لا تُعاد قيمة إلا بعد الحفظ (مراجعة SQL):** في `submit_order` تأتي `return v_id` **بعد** إدراج `orders` وإدراج `order_idem`، وكلها في معاملة الدالة الواحدة؛ أي فشل قبل الإرجاع يتراجع عن الاثنين معاً (مُختبَر محلياً: فشل مفتعل ← 0 طلب و0 سجل idem، ثم نجاح عند الإعادة).

**الإعادة:** الحمولة تحمل `p.idem` دائماً؛ لكن الدالة المنشورة قد تكون قديمة وتتجاهله ← لذلك الإعادة التلقائية معطّلة افتراضياً (`CONFIG.SB_IDEMPOTENT=true` يفعّلها) وعند غيابها `safeRetry=false` فلا يُعرض زر «إعادة المحاولة» ويُطلب التأكد عبر واتساب (رسالة فقط).

**الاختبارات (56 في `phase12b1c-client.js`):** معرّف صالح؛ نص فارغ؛ جسم فارغ؛ 6 معرّفات مشوَّهة؛ 6 أشكال JSON غير متوقعة؛ JSON تالف؛ 204؛ ردّ من RPC آخر؛ إعادة توجيه؛ HTTP 401/403/409/422/429/400×2؛ 500/502/503؛ `try_again`؛ انقطاع بعد تنفيذ المعاملة ثم إعادة بنفس المفتاح تعيد الأصل (طلب واحد)؛ إعادة تلقائية مع `SB_IDEMPOTENT`؛ تغيّر المحتوى ← مفتاح جديد؛ نفس المفتاح بمحتوى مختلف ← `REJECTED idempotency_key_reuse`.
**الحالة: PARTIAL** — هذه اختبارات منطق العميل مقابل **خادم وهمي بشكل ردود PostgREST الموثَّقة**، وليست PostgREST/Supabase حقيقياً. منطق SQL نفسه اختُبر على PostgreSQL 16 محلي معزول (`platform/supabase/tests/local/run-order-idem.sh`، أُعيد تشغيله اليوم: معرّف واحد=طلب واحد، 5 تصادمات ← `try_again` بلا آثار، 12 جلسة متزامنة ← طلب واحد) بمصادقة Supabase مستبدلة بمُجسَّات ← PARTIAL أيضاً. **Supabase الحقيقي: BLOCKED**، ولم يُطبَّق أي SQL عليه.

### B — سلامة معرّف الطلب اليدوي
| الخلفية | من يولّد المعرّف؟ | شرط النجاح |
|---|---|---|
| PHP | **الخادم** (`newOrderId`، بادئة `M`) | `ok:true` + معرّف صالح (عقد PHP) |
| Supabase (يدوي) | **العميل** (من المفتاح العشوائي الآمن: `M<yymmdd>-<10hex>`) — وصفه كذلك الآن (`idOrigin:"client"`) ولا يُوصَف كمولَّد خادمياً | HTTP 2xx + قراءة صف واحد يطابق المعرّف والاسم والهاتف والمجموع والمجموع الفرعي |
| Supabase (RPC للزبائن) | الخادم (دالة SQL) | عقد A أعلاه |
| Sheets | لا معرّف | `UNKNOWN` دائماً، لا معرّف مختلق |

- **لا معرّف بديل:** حُذف كل توليد معرّف عشوائي لكل محاولة؛ المعرّف مشتق من المفتاح فإعادة المحاولة بعد ضياع الردّ تستعمل المعرّف نفسه فتعطي 409 ثم قراءة تأكيدية ← `DUPLICATE_CONFIRMED` (الصف المطابق) أو `REJECTED id_conflict` (صف مختلف) أو `UNKNOWN` (تعذّرت القراءة).
- حالات الفشل مُختبَرة (16 اختباراً): 500/503، صفّ غير مُعاد (`[]`)، جسم فارغ بعد 201، كائن بدل مصفوفة، صف بمحتوى مختلف، 401/403/422، بلا جلسة مدير (لا طلب شبكة)، ضياع الردّ ثم إعادة، 409 بمحتوى مختلف، 409 ثم تعذّر القراءة.
- **حدّ معروف (غير مُصلَح عمداً، لا تغيير واسع):** إعادة بعد منتصف الليل داخل نافذة المفتاح (30 دقيقة) تغيّر بادئة التاريخ ← معرّف آخر (احتمال طلب مكرّر نادر على Supabase اليدوي فقط).
- **الحالة:** PHP ← PASS (متصفح حقيقي، C3). Supabase اليدوي ← **PARTIAL** (vm مقابل خادم وهمي)، **NOT TESTED في المتصفح** (لا بيئة Supabase).

**12B.1 مُغلقة ضمن النطاق المُختبَر**: كل شروط القبول المنصوص عليها تحققت لمسارات PHP كلها (سلة، صفحة منتج، رقمي، Upsell، يدوي) بإثبات متصفح حقيقي وقاعدة بيانات حقيقية، ولعقد Supabase توثيق واختبارات مناسبة مع إبقاء الاختبار الحقيقي **BLOCKED** كما طُلب. لا يعني الإغلاق أن البنود BLOCKED / PARTIAL / NOT TESTED في §4 و§7 صارت ناجحة — هي باقية مفتوحة، أهمها: تشغيل `schema.sql` المحدَّث على مشروع Supabase اختباري واختبار PostgREST حقيقي قبل أي ادعاء بأن متاجر Supabase مغطّاة، وقرار `SB_IDEMPOTENT`.
