# تدقيق هندسة الكود وقابلية التوسع — ALYSSUM DZ

- **تاريخ المراجعة:** 2026-10-31
- **المستودع:** https://github.com/saberbalbouzi-ui/alyssumdz
- **الفرع:** `main`
- **Commit الذي بُنيت عليه المراجعة:** `2d214ec29ab8b9530b95614df9c21ba59d5bde84`
- **النطاق:** هندسة الكود، حدود الوحدات، مسارات الطلب، قاعدة البيانات، الأحداث والمهام المجدولة، موزّع المتاجر، وبناء لوحة الإدارة.
- **نوع التدقيق:** مراجعة ساكنة لملفات التنفيذ والاختبارات والتصميم. لم يتم تشغيل اختبارات الأداء أو قياس الإنتاج.

> **حدود التقرير:** لا توجد هنا أرقام throughput أو latency مختلقة. كل استنتاج عن السعة هو استنتاج من بنية التنفيذ، ويجب إثباته باختبارات حمل وقياسات فعلية قبل تحديد عدد المتاجر الممكن استضافتها.

## 1. الملخص التنفيذي

المنصة ليست كتلة عشوائية؛ لديها تصميم **Modular Monolith** واضح: Worker واحد للـAPI، وحدات نطاق مستقلة، مخطط جداول ببادئات، صندوق أحداث، واختبارات حدود تمنع بعض أشكال الاقتران بين الوحدات. هذا أساس جيد للتطوير التدريجي ولا أوصي بإعادة كتابة المشروع إلى Microservices الآن.

لكن توجد حدود توسع واضحة في تنفيذ النواة:

1. توجيه API يمر على قائمة المسارات خطياً في كل طلب.
2. cron يعالج الأحداث والمهام بشكل تسلسلي، ويقرأ 50 حدثاً فقط في الدورة.
3. مخزن نتائج المضيفين في tenant-router هو Map غير محدود الحجم، ويحتفظ بنتائج الربط لمدة 60 ثانية.
4. غلاف DB.batch لديه مسار بديل ينفذ الأوامر بالتتابع، وهو غير ذري.
5. نموذج التشغيل الحالي Worker + D1 واحدة يحتاج خطة قياس وحدود واضحة قبل التوسع الكبير.
6. لوحة الإدارة تحتوي على مخرجات build مولّدة تدمج أجزاء كبيرة في ملف HTML، ما يجعل تجربة التطوير والتحميل والتصحيح أصعب إذا لم تُفصل بوضوح بين source وartifact.

**الحكم:** المعمارية قابلة للتوسع تدريجياً، لكن قابلية التوسع لم تُثبت بالأرقام. الأولوية هي تحسين مسارات النواة والمهام الخلفية وإضافة observability واختبارات الحمل، لا تفكيك المنصة فوراً إلى خدمات صغيرة.

## 2. خريطة المعمارية التي تظهر في الكود

### 2.1 منصة API

في `platform/api/src/index.js` تُسجل الوحدات في مصفوفة واحدة، ومنها:
- admin وplatform
- commerce وpayments وwallet
- hooks وcapi وwhatsapp وsms
- antifraud وads وadsoauth
- digital وsources وcarts وab وtryon
- agency وappstore وmarketplace

وتُمرر إلى `createPlatform()` في `core.js`.

### 2.2 حدود الوحدات

ملف `platform/api/ARCHITECTURE.md` يحدد قواعد مهمة:
- لكل وحدة بادئة جداول خاصة.
- لا تكتب الوحدة في جداول وحدة أخرى.
- التواصل بين الوحدات عبر الأحداث، مع استثناءات موثقة.
- توجد اختبارات حدود في `test/boundaries.test.mjs`.

هذه قرارات هندسية صحيحة وتقلل كلفة فصل الوحدات لاحقاً. يجب الحفاظ عليها كقواعد CI إلزامية.

### 2.3 طبقة التوجيه

النواة تسجل المسارات في مصفوفة `routes`، وتحوّل الأنماط إلى RegExp عند بناء التطبيق. هذا يبسط إضافة الوحدات، لكن طريقة البحث عن المسار وقت الطلب خطية.

### 2.4 الأحداث والمهام

الأحداث تُكتب في `pf_events`، ثم cron يوزعها على handlers الوحدات مع حفظ تقدم كل handler وإعادة المحاولة بتأخير متزايد. الفكرة جيدة وظيفياً، لكن التنفيذ التسلسلي يضع سقفاً على throughput.

### 2.5 توزيع المتاجر

`platform/worker/tenant-router.js` يحدد المتجر من hostname، ويقرأ مصدر المحتوى من Supabase RPC، ثم يقدّم الملفات من GitHub Pages أو Supabase Storage. توجد ذاكرة محلية لنتائج المضيفين وCache API لمحتوى المواقع.

## 3. النتائج والمشكلات

### E-01 — البحث عن route خطي لكل طلب API

**الشدة:** متوسطة (Medium)
**الثقة:** عالية — السلوك ظاهر في الكود.

**الملف:** `platform/api/src/core.js`، داخل `dispatch()`.

**الدليل:**
بعد معالجة المسارات العامة، ينفذ الكود:
```js
for (const rt of routes) {
  if (rt.method !== m) continue;
  const mm = rt.re.exec(p);
  if (!mm) continue;
  // auth + handler
}
```
المسارات تُجمع من الوحدات عند `createPlatform()`، لكن لا يوجد فهرس بحسب method أو path prefix أو route trie. لذلك قد يفحص الطلب عدداً كبيراً من RegExp قبل العثور على المسار.

**الأثر مع النمو:**
كلما زاد عدد endpoints والوحدات، زاد عمل CPU في مسار كل طلب، حتى عندما يكون handler نفسه سريعاً. هذا ليس bottleneck مثبتاً عند الحجم الحالي، لكنه نمط O(R) لكل request حيث R عدد المسارات.

**الإصلاح:**
1. بناء خريطة أولية حسب HTTP method.
2. تجميع المسارات بحسب أول segment ثابت، مثل `/v1/orders` و`/admin`.
3. إذا زاد الحجم لاحقاً، اعتماد trie/router radix.
4. الاحتفاظ بترتيب الأولوية الحالي واختبار تعارض المسارات الديناميكية.
5. إضافة benchmark يقارن 50 و150 و500 و1000 route.

**معيار القبول:** نتائج benchmark تثبت أن إضافة وحدات ومسارات لا ترفع زمن routing بصورة خطية غير مقبولة.

### E-02 — cron يعالج صندوق الأحداث بالتتابع وبحد 50 حدثاً لكل دورة

**الشدة:** عالية عند زيادة حجم الأحداث (High under load)
**الثقة:** عالية — السلوك ظاهر في الكود.

**الملف:** `platform/api/src/core.js`، الدوال `cron()` و`runEvent()`.

**الدليل:**
- الاستعلام يقرأ: `ORDER BY id LIMIT 50`.
- ثم ينفذ: `for (const e of rows) await runEvent(...)`.
- داخل كل حدث، ينفذ handlers بالترتيب: `for (const h of ...handlers) await h.fn(...)`.
- بعد معالجة الأحداث، يستدعي cron لكل وحدة تملك `m.cron` بالتتابع.

**الأثر:**
إذا وصل عدد الأحداث أسرع من معدل معالجتها، سيتراكم backlog في `pf_events`. كما أن handler بطيئاً أو مزوداً خارجياً بطيئاً قد يؤخر بقية handlers والأحداث والدورات اللاحقة. حد 50 يحد حجم العمل في الدورة، لكنه لا يضمن تصريف الطابور.

**الإصلاح:**
1. فصل جدولة الأحداث عن مهام مزامنة الوحدات.
2. إضافة مؤشرات: oldest pending age، pending count، attempts، failed count، event processing duration.
3. إضافة lease/claim آمن للأحداث حتى لا تعالجها أكثر من نسخة بالتوازي.
4. اعتماد دفعات محدودة متوازية بعد التأكد من idempotency وترتيب الأحداث لكل aggregate/tenant.
5. وضع timeout لكل handler، ونقل الاتصالات البطيئة إلى outbox delivery مستقل.
6. توفير dead-letter queue وإعادة تشغيل يدوية مراقبة للأحداث الفاشلة.

**معيار القبول:** اختبار حمل ينتج أحداثاً أكثر من 50 لكل دورة ويثبت أن الطابور يعود إلى الصفر أو يبقى ضمن SLO محدد، دون فقد أو تكرار غير صحيح.

### E-03 — tenant-router يحتفظ بذاكرة host lookup غير محدودة

**الشدة:** متوسطة (Medium)
**الثقة:** عالية — لا يوجد حد أقصى ظاهر للـMap.

**الملف:** `platform/worker/tenant-router.js`.

**الدليل:**
```js
const LOOKUP_TTL = 60_000;
const memo = new Map(); // host -> {t, v}
...
if (!v.error) memo.set(host, { t: Date.now(), v });
```
النتائج التي لا تحمل error تُخزن، بما فيها نتائج المضيف غير المعروف. لا يظهر حد أقصى لحجم Map ولا تنظيف شامل للمفاتيح المنتهية؛ انتهاء TTL يمنع استعمال القيمة القديمة لكنه لا يحذف المفتاح تلقائياً.

**الأثر:**
إذا أمكن إرسال طلبات بأسماء مضيفين كثيرة إلى هذا الـWorker، يمكن أن يتزايد عدد المفاتيح في ذاكرة isolate مع الوقت. كما أن نتيجة المضيف (بما فيها unknown/status/source) قد تبقى محلية حتى 60 ثانية.

**الإصلاح:**
- استبدال Map بـLRU محدود الحجم (مثلاً حد مضبوط وقابل للقياس).
- حذف العناصر المنتهية دورياً عند الوصول أو باستخدام سياسة eviction.
- عدم تخزين unknown hosts أو إعطاؤها TTL أقصر بكثير.
- إضافة حد لحجم hostname والتحقق الصارم من صيغته.
- توثيق أن تغيير source أو تعليق متجر قد يتأخر حتى انتهاء TTL، أو توفير invalidation عند التغيير إذا كانت هناك حاجة لتعطيل فوري.

**معيار القبول:** اختبار يرسل آلاف hostnames مختلفة ويثبت أن الذاكرة المحلية لا تنمو بلا حد، وأن إيقاف متجر يسري ضمن زمن معلن.

### E-04 — DB.batch ينفذ بالتتابع إذا لم تتوفر D1 batch

**الشدة:** متوسطة (Medium)
**الثقة:** عالية — fallback ظاهر في الكود.

**الملف:** `platform/api/src/core.js`، class `DB`.

**الدليل:**
```js
async batch(list) {
  for (let i = 0; i < list.length; i += 50) {
    const part = list.slice(i, i + 50);
    if (typeof this.d1.batch === "function")
      await this.d1.batch(part.map(([sql, ...a]) => this.stmt(sql, a)));
    else
      for (const [sql, ...a] of part)
        await this.stmt(sql, a).run();
  }
}
```
المسار البديل ينفذ statements واحدة تلو الأخرى ولا يوفر معاملة ذرية شاملة. كما أن test harness في `platform/api/test/_harness.mjs` ينشئ adapter اختبارياً لا يعرّف `d1.batch`، لذلك كثير من اختبارات الوحدات تسير عبر fallback التسلسلي لا عبر semantics الفعلية لـD1 batch.

**الأثر:**
الاختبارات قد تمرّ دون أن تثبت atomicity في بيئة D1 الحقيقية، كما أن تشغيل عمليات كثيرة عبر fallback أبطأ وقد يترك بيانات جزئية عند فشل statement وسط الدفعة.

**الإصلاح:**
1. جعل دعم batch/transaction جزءاً صريحاً من عقد DB في الإنتاج.
2. عدم استخدام fallback الصامت في المسارات التي تتطلب atomicity.
3. توفير adapter اختبار يحاكي D1 batch transaction behavior أو اختبارات تكامل فعلية على D1 staging.
4. توثيق العمليات التي تقبل partial completion وتلك التي لا تقبله.
5. إضافة اختبارات فشل عند statement رقم N.

**معيار القبول:** كل عملية تتطلب all-or-nothing تفشل بالكامل أو تنجح بالكامل في D1 staging.

### E-05 — cron يجمع الأعمال الخلفية غير المتجانسة في دورة واحدة

**الشدة:** متوسطة (Medium)
**الثقة:** عالية — ترتيب التنفيذ ظاهر.

**الملف:** `platform/api/src/core.js`.

**الدليل:**
بعد معالجة 50 حدثاً، يستدعي `cron()` كل `m.cron(ctx)` بالتتابع ويجمع النتيجة. الوحدات قد تقوم بمزامنة APIs خارجية أو معالجة سجلات، وهي أعمال تختلف في زمن التنفيذ وحدودها ومعدلات فشلها.

**الأثر:**
تأخر مهمة واحدة يمكن أن يؤخر بقية المهام. كما يصعب تحديد ميزانية وقت مستقلة لكل نوع عمل أو توسيع مهمة معينة دون زيادة حمل بقية المنصة.

**الإصلاح:**
- فصل cron حسب نوع المهمة وتواترها.
- جعل كل مهمة قصيرة ومحدودة بميزانية وقت/عدد سجلات.
- حفظ cursor/checkpoint بعد كل صفحة.
- اعتماد queue مستقلة للمهام الطويلة أو كثيفة الاتصالات.
- وضع قياس زمن لكل وحدة ومهمة.

**معيار القبول:** لا تؤخر مزامنة مزود خارجي مهام المحفظة أو أحداث الطلبات الحرجة، وتكون لكل مهمة سياسة retry وtimeout مستقلة.

### E-06 — تصميم Worker + D1 واحدة يحتاج خطة سعة قبل آلاف المتاجر

**الشدة:** تخطيطية (Architecture scaling risk)
**الثقة:** عالية أن النمط الحالي موجود؛ لا توجد أرقام تثبت حد السعة.

**المواضع:**
- `platform/api/src/index.js`
- `platform/api/src/core.js`
- `platform/api/ARCHITECTURE.md`

**الدليل:**
التصميم الحالي يركّب الوحدات كلها داخل Worker API واحد ويتعامل مع D1 واحدة عبر `env.DB`. هذا Modular Monolith، وليس مجموعة خدمات مستقلة أو قواعد بيانات موزعة.

**الأثر:**
- كل الوحدات تشترك في ميزانية تنفيذ Worker وقاعدة D1 نفسها.
- استعلامات التقارير والمزامنة الثقيلة قد تنافس عمليات الطلب والدفع.
- قد يصبح حجم الجداول والفهارس وعمليات cron ونمو صندوق الأحداث عوامل ضغط مشتركة.
- فصل وحدة إلى خدمة مستقلة مستقبلاً يتطلب حدود بيانات وأحداث واضحة.

**لا أعتبر ذلك خطأً بحد ذاته.** هذا خيار مناسب لمرحلة MVP وبداية النمو، ولا يوجد دليل في هذا التدقيق على أن D1 الحالية وصلت إلى حدها.

**الإصلاح/خطة التطور:**
1. الإبقاء على Modular Monolith الآن.
2. قياس استهلاك D1: query latency، rows scanned، write volume، database size، busy/retry errors.
3. فصل read-heavy analytics عن مسارات checkout/payment.
4. استخدام جداول تلخيص/rollups للتقارير بدلاً من عمليات مسح كبيرة على كل طلب.
5. عند ظهور bottleneck مثبت، فصل أكثر الوحدات استقلالاً (مثلاً gateway أو event delivery أو analytics) دون تكرار ملكية البيانات.
6. تصميم partitioning/tenant sharding فقط عند وجود قياسات تبررها، لا بشكل مبكر.

**معيار القبول:** وجود تقرير سعة مبني على اختبارات حمل وبيانات D1 فعلية، مع حدود تنبيه قبل بلوغ سقف الخدمة.

### E-07 — ملف لوحة الإدارة مخرج build كبير ومتشابك مع مصادر متعددة

**الشدة:** منخفضة إلى متوسطة (Low/Medium)
**الثقة:** عالية في أسلوب البناء؛ أثر الأداء يحتاج قياس متصفح.

**المواضع:**
- `admin.html`
- `scripts/build-admin-pb.py`
- `scripts/pagebuilder*.js`
- `assets/js/admin-*.js`
- `platform/README.md`

**الدليل:**
- `platform/README.md` يوضح أن `admin.html` وملفات `assets/js/admin-*.js` وCSS ما زالت خارج `platform/` لأنها لوحة مشتركة تُشحن للعملاء.
- `scripts/build-admin-pb.py` يقرأ مجموعة كبيرة من ملفات pagebuilder ويجمعها في كتلة script داخل `admin.html` بين PB:start وPB:end.
- السكربت يحدّث بصمات بعض الملفات لكسر الكاش، لكن كتلة Page Builder نفسها مضمّنة inline داخل HTML.

**الأثر:**
- تضخم HTML الأولي وتحليل JavaScript كبير عند فتح اللوحة.
- صعوبة تحديد أخطاء runtime ومصدرها في artifact المدمج.
- خطر اختلاف source عن artifact إذا نُسي تشغيل build.
- تحميل أدوات لا يحتاجها المستخدم في كل جلسة، ما لم تكن هناك آلية تحميل كسول أخرى.

**الإصلاح:**
1. جعل ملفات المصدر هي المرجع الوحيد، واعتبار `admin.html` artifact مولداً.
2. نقل Page Builder إلى bundle مستقل hashed بدل inline script.
3. تحميل الوحدات الثقيلة lazy عند فتح الأداة فقط.
4. إضافة build verification في CI يفشل إذا كان artifact غير محدث.
5. قياس LCP/INP/JS parse time وحجم النقل على جهاز متوسط واتصال بطيء.
6. فصل لوحة المزوّد عن لوحة التاجر في bundles مستقلة إذا لم يكن ذلك قد تم بالفعل.

**معيار القبول:** لا تُحمّل حزمة Page Builder الثقيلة عند فتح لوحة التاجر إلا عند الحاجة، وتكون artifact reproducible من ملفات المصدر.

## 4. نقاط قوة هندسية يجب الحفاظ عليها

1. **Modular Monolith:** أفضل من تفكيك مبكر إلى Microservices.
2. **قواعد ملكية الجداول:** بادئات الوحدات واختبارات الحدود تقلل coupling.
3. **Event outbox:** `pf_events` مع extId وإعادة المحاولة وتقدم كل handler أساس جيد للتكاملات.
4. **Idempotency:** وجود `Idempotency-Key` في النواة للمسارات التي تعلن `idem` يقلل تكرار عمليات الكتابة.
5. **Pagination:** توجد دالة cursor pagination في النواة؛ يجب تعميمها على جميع القوائم الكبيرة وعدم استخدام OFFSET على جداول ضخمة.
6. **حدود بعض عمليات المزامنة:** توجد حدود صفحات/صفوف في وحدات مثل `sources.js` و`ads.js`، وهذا اتجاه صحيح.
7. **اختبارات حدود الوحدات:** يجب أن تبقى شرطاً إلزامياً قبل دمج أي وحدة.

## 5. خطة تحسين مرتبة

### P0 — قبل التوسع في عدد المتاجر
- [ ] إضافة metrics لـAPI وD1 وcron وevent backlog.
- [ ] وضع LRU محدود لذاكرة host lookup.
- [ ] تحديد SLO لزمن تعطيل متجر بعد تغيّر حالته.
- [ ] إضافة اختبار حمل للـAPI والـcron على بيئة staging.
- [ ] التأكد أن D1 batch هو المسار المستخدم في الإنتاج للعمليات الذرية.

### P1 — تحسين throughput
- [ ] فهرسة route lookup حسب method وprefix.
- [ ] فصل event processing عن cron الخاص بالوحدات.
- [ ] إضافة leases/claims للأحداث ومعالجة متوازية محدودة.
- [ ] وضع timeout وretry وdead-letter لكل handler.

## 6. مصفوفة اختبارات الأداء المطلوبة

| الاختبار | السيناريو | ما يجب قياسه |
|---|---|---|
| API routing | 50/150/500/1000 routes | p50/p95/p99 وزمن CPU |
| Tenant lookup | 1k/10k/50k hostnames | hit ratio، miss latency، ذاكرة cache |
| Event backlog | 50/500/5k/50k events | drain rate، oldest age، retry count |
| Cron contention | مهام خارجية بطيئة مع أحداث طلبات | تأخر الأحداث الحرجة |
| D1 reads | قوائم الطلبات والتقارير مع بيانات كبيرة | query latency، rows scanned |
| D1 writes | طلبات متزامنة وحجز مخزون | write latency، conflicts، retries |
| Admin frontend | جهاز متوسط واتصال محدود | JS transfer، parse/eval، LCP، INP |
| Multi-tenant load | 100/500/1000 متجر اصطناعي | عزل البيانات، latency، أخطاء 429/5xx |

لا ينبغي تحويل أرقام المتاجر في الجدول إلى وعود تسويقية قبل تنفيذ الاختبارات.

## 7. التوصية المعمارية

**لا تعِد كتابة المنصة، ولا تفككها إلى Microservices الآن.**

احتفظ بالهيكل الحالي:
- API Worker كنواة Modular Monolith.
- وحدات نطاق بملكية جداول واضحة.
- أحداث بين الوحدات.
- Gateway مستقل حيث يوجد سبب تشغيلي.
- Tenant Router مستقل لتقديم المواقع الثابتة.

ثم عالج أولاً:
1. Observability وقياس السعة.
2. Event processing والـcron.
3. Tenant cache bounded/invalidation.
4. Route indexing وDB batch guarantees.
5. Lazy loading للوحة الإدارة.

بعد ظهور قياسات تثبت bottleneck، افصل الخدمة المتسببة وحدها. المرشح الطبيعي للفصل غالباً هو event delivery/worker jobs أو analytics، وليس commerce أو wallet عشوائياً؛ لأن المال والطلبات يستفيدان من بقاء قواعدهما متماسكة.

## الخلاصة

هندسة ALYSSUM DZ أفضل من مشروع CRUD تقليدي: فيها نواة، وحدات، ملكية بيانات، أحداث، واختبارات حدود. نقطة الضعف ليست غياب المعمارية، بل أن بعض المسارات المركزية ما زالت تنفذ عملاً تسلسلياً أو خطياً، وأن سعة التشغيل غير مثبتة باختبارات حمل.

**القرار المقترح:** تحسين النواة الحالية وإثباتها بالقياس، مع الحفاظ على Modular Monolith. لا تبدأ إعادة كتابة أو تقسيم الخدمات قبل أن تكشف metrics عن عنق زجاجة حقيقي.
