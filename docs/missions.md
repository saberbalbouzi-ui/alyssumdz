# مهام مؤجَّلة للتنفيذ لاحقاً (من صاحب المتجر)

> سجلّ مهام مطلوبة بأمر صاحب المتجر لتُنفَّذ لاحقاً. **لا تنفَّذ تلقائياً**: تُرتَّب بأمره أو عند بدء مرحلة مناسبة. كل مهمة فيها: الفكرة، ما نملكه اليوم، المطلوب، ما يجب التحقق منه قبل البناء، ومعيار القبول. الحالة: ⏳ للتنفيذ لاحقاً · 🔨 جارية · ✅ مُنجزة. أُضيفت: 2026-10-13.
> **تنبيه صدق:** وُصفت الجهات التالية (Chargily، Fatoura، MobiSpace…) في رسالة صاحب المتجر نقلاً عن مصدر خارجي؛ **لم يُتحقق من وثائقها أو أسعارها أو شروطها** — يُقرأ التوثيق الرسمي قبل أي بناء، ولا تُكتب صيغ طلبات من الذاكرة.

## M1 — الدفع الإلكتروني (إلهام: Chargily Pay) ⏳
- **الفكرة:** زر «فعّل الدفع بالبطاقة الذهبية/CIB» في اللوحة يولّد روابط دفع (Pay by Link) أو checkout مباشراً، فلا يحتاج التاجر ملفاً بنكياً معقداً.
- **اليوم:** المدفوعات في `admin-payments.js` تتبع الدفع عند الاستلام يدوياً/تلقائياً بحالة الشحن؛ لا بوابة دفع إلكتروني. حدث `payment.confirmed` موجود في منصة API (يُشغّل الروابط الرقمية).
- **المطلوب:** وحدة `pay` في منصة API (`saas/platform/src/modules/pay.js`): تكامل مشفّر `chargily` (مفتاح سرّي لكل تاجر)، إنشاء رابط دفع لطلب، استقبال webhook موقَّع ← `payment.confirmed` ← (يفعّل المنتج الرقمي/يحدّث الطلب)، وزر/بطاقة في اللوحة. 
- **تحقق قبل البناء:** وثائق Chargily الرسمية (نقاط API، توقيع webhook، العمولات، شروط التاجر)، هل تحتاج كل تاجر حساب Chargily خاصاً (على الأرجح نعم → نمط BYOK كالشحن)، والجوانب القانونية للتحصيل.
- **القبول:** طلب بمبلغ → رابط → دفع تجريبي (sandbox) → حدث `payment.confirmed` واحد (idempotent) → حالة الطلب «مدفوع»؛ اختبارات بمحاكاة + تجربة sandbox حقيقية بإذن.

## M2 — فواتير قانونية (إلهام: Fatoura) ⏳
- **الفكرة:** مولّد فواتير مطابقة للقانون الجزائري (TVA، حقوق الطابع، رقم السجل التجاري NIF/RC/NIS) لتاجر B2B أو علامة تحتاج تتبعاً قانونياً.
- **اليوم:** `admin-order-docs.js` يطبع فاتورة A4 وبوليصة A6 مع باركود (بلا ضرائب ولا بيانات قانونية ولا ترقيم متسلسل).
- **المطلوب:** إعدادات هوية قانونية للمتجر (الاسم القانوني، العنوان، NIF/RC/NIS/AI)، ترقيم متسلسل لا ينقطع بالسنة، حساب TVA (نسبة قابلة للضبط) وحقوق الطابع، فاتورة PDF/طباعة، تصدير سجلّ الفواتير (CSV) للمحاسب، واسترجاع/إلغاء بفاتورة دائنة.
- **تحقق قبل البناء (محاسب/قانون):** النسب والشروط الفعلية (TVA 9/19%، حقوق الطابع على الدفع النقدي وحدوده)، الصيغة الإلزامية للفاتورة، مدة الحفظ، وهل التاجر الصغير (auto-entrepreneur/IFU) معفى. **لا تُكتب نسبة من الذاكرة** — اطلب من صاحب المتجر مراجعة محاسبه.
- **القبول:** ترقيم متسلسل بلا فجوات (اختبار تزامن)، أرقام الضريبة تطابق حساباً مستقلاً، وقالب يمر مراجعة المحاسب.

## M3 — العنوان بدبوس GPS (إلهام: Yassir/Coursa) ⏳
- **الفكرة:** عند الطلب يضع الزبون دبوساً على الخريطة بجانب (أو بدل) حقل العنوان؛ يتحول إلى رابط خريطة على البوليصة والطلب فيصل الموزّع أسرع وتنخفض المرتجعات (NPAI).
- **اليوم:** نموذج الطلب (`app.js`) ولاية + بلدية + عنوان نصي؛ لا إحداثيات.
- **المطلوب:** خريطة OpenStreetMap (Leaflet، بلا مفتاح ولا تكلفة) اختيارية في نموذج الطلب مع «حدّد موقعي» (Geolocation) ؛ حفظ `lat/lng` في `extra["📍 الموقع"]` للطلب؛ رابط `https://maps.google.com/?q=lat,lng` في معاينة الطلب والبوليصة وفي حقل ملاحظات الطرد عند الإرسال للشركة؛ قياس: نسبة الطلبات بدبوس ونسبة مرتجعاتها مقابل غيرها.
- **تحقق قبل البناء:** وزن المكتبة على الجوال (تحميل كسول فقط عند الفتح)، سياسة بلاط OSM (الاستعمال المعتدل أو مزوّد بلاط)، موافقة الخصوصية (القانون 18-07: الموقع بيانات شخصية، يُطلب بموافقة صريحة ويُحذف مع الطلب)، وهل تقبل شركات التوصيل حقلاً للإحداثيات (يُدرَج في الملاحظة بدل الحقل).
- **القبول:** دبوس يُحفظ ويظهر رابطاً صحيحاً في الطلب والبوليصة؛ النموذج يعمل بلا دبوس (غير إلزامي)؛ لا تتجاوز الصفحة زيادة وزن مقبولة قبل فتح الخريطة.

## M4 — إشعارات SMS (إلهام: MobiSpace/Lintel/SMS.dz) ⏳
- **الفكرة:** SMS تلقائي عند إنشاء الطلب وتغيّر حالة الطرد، باسم مرسل مخصص (مثل «ALYSSUM»)، و«رصيد SMS» يُباع للتجار كمصدر دخل للمنصة.
- **اليوم:** إشعارات واتساب بنقر يدوي (`notify.json`)؛ وحدة `whatsapp` في منصة API (تحتاج حساب Business). لا SMS.
- **المطلوب:** وحدة `sms` في منصة API: تكامل مشفّر لمزوّد SMS (واجهة محوّل عامة كمحوّلات الشحن)، قوالب بمتغيّرات (`{name} {order_id} {tracking}`)، تشغيل على أحداث `order.created/confirmed` و`shipment.status_changed`، **سجلّ رصيد لكل مستأجر** (خصم عند الإرسال، منع الإرسال بلا رصيد، تنبيه نفاد)، تقرير تسليم، وحدّ معدّل لمنع الإساءة.
- **تحقق قبل البناء:** مزوّد فعلي له API موثّقة ويقبل شروطنا (اختيار بعد قراءة وثائق وأسعار عدة مزوّدين)، تسجيل اسم المرسل لدى المشغّلين/السلطة المنظمة وهل يلزم لكل مستأجر، قيود المحتوى والإشعار التسويقي مقابل المعاملاتي، الموافقة وإلغاء الاشتراك (STOP)، والتسعير/الفوترة لعملاء المنصة (يحتاج بوابة دفع M1 أو تحويلاً يدوياً).
- **القبول:** حدث ← SMS واحد (idempotent) ← خصم رصيد ← سجلّ؛ رصيد صفر لا يرسل؛ اختبارات بمحاكاة ثم رسالة حقيقية واحدة بإذن.

## M5 — «وضع مركز الاتصال» (Call Center Mode) ⏳
- **الفكرة:** واجهة سريعة مستقلة لعاملات التأكيد: طلبات جديدة، أزرار نقرة واحدة (مؤكَّد، لم يُجب محاولة 1/2/3، لاحقاً، رقم خاطئ، ملغى)، ونقرة على الرقم تفتح الاتصال أو واتساب ويب.
- **اليوم (موجود جزئياً):** قائمة «نتيجة الاتصال» في الطلبات ومعاينتها (`orderAction`/`previewResult`) بالحالات نفسها؛ ترتيب الطلبات تلقائياً (الجديد أولاً)؛ أزرار `📞 اتصل`/`💬 واتساب`؛ فحص المخزون قبل التأكيد؛ حظر العملاء السيّئين؛ مزامنة Google Sheets في منصة API (`sheets`).
- **المطلوب:** صفحة/تبويب «مركز الاتصال» بتصميم قوائم لا جداول: بطاقة طلب واحدة بالدور (تاريخ، زبون، ولاية، مبلغ، منتجات) وأزرار كبيرة للجوال، عدّاد المتبقي، مؤقت آخر محاولة، ملاحظة صوتية/نصية، «التالي» تلقائي بعد القرار، **حسابات عاملات بصلاحية محدودة** (لا ترى المالية ولا الإعدادات) وإحصاء لكل عاملة (مؤكَّد/ساعة، نسبة التأكيد) لمكافآت الأداء، وتسجيل من أكّد ومتى (تدقيق).
- **تحقق قبل البناء:** الأدوار والصلاحيات اليوم محصورة بمدير واحد (`is_admin`) — الأدوار الفرعية تحتاج تصميماً في Supabase (RLS) وPHP؛ يوصى ببدء الواجهة للمدير ثم إضافة الأدوار كمرحلة ثانية.
- **القبول:** معالجة 100 طلب بنقرات قليلة بلا تمرير جدول؛ كل قرار يمرّ بالمنطق الحالي نفسه (لا منطق موازٍ)؛ اختبار Playwright للمسار على الحاسوب والجوال.

## ترتيب مقترح (قابل للتغيير بأمر صاحب المتجر)
1. **M5** (يعتمد على موجود، أثر يومي مباشر، بلا اعتماد خارجي).
2. **M3** (يخفض المرتجعات؛ بلا حساب خارجي).
3. **M4** ثم **M1** (يحتاجان اختيار مزوّد وقراءة وثائقه، ويشتركان في الفوترة/الرصيد).
4. **M2** (يحتاج مراجعة محاسب قبل البناء).
