# سطر «📍 عنوان المكتب» وبصمة الطلب (12B.1) — تحليل Idempotency واختبارات (**غير معتمد**)

> **الحالة: قيد المراجعة، لا يُعتمد قبل قرارك.** فرع `site/12b-order-truth` يحمل الدمج الحالي **مؤقتاً** (الخيار A أدناه) لأنه الوحيد المتسق دون تعديل خادم. لا Push ولا Merge ولا Deploy.

## 1) ما هو التعديل (Diff)
`main` أضاف في مسار صفحة المنتج (`initProduct`) سطراً يلصق عنوان المكتب في `order.extra` قبل `PFOrder.prep`. 12B.1 غيّرت اشتقاق المفتاح بعد بناء الطلب. دمجتُ الاثنين بإبقاء سطر العنوان **قبل** `API.orderKey`:
```diff
     if(desk){ const __da = deskAddrOf(state.wilaya, desk, commune); if(__da) __order.extra["📍 عنوان المكتب"] = __da; }
-    const __pfr = window.PFOrder ? PFOrder.prep(__order) : "";
+    const __ik = await API.orderKey(__order);
+    if(__grp){ __grp = Upsell.gid(__ik); __order.extra["🧺 مجموعة"] = __grp; }
+    const __pfr = window.PFOrder ? PFOrder.prep(__order, __ik) : "";
```
(مسار السلة `Cart.checkout` لا يحوي سطر العنوان فلا يتأثر.)

## 2) كيف يعمل المفتاح والبصمة (من الشيفرة الفعلية)
- **العميل (`OrderTruth` في `api.js`):** `keyFor(order)` يحسب «خانة» = `sha256(salt|canon(order))` ويخزّن تحتها **مفتاحاً عشوائياً** في `localStorage` لمدة 30 دقيقة. `canon` يشمل: الاسم والهاتف والولاية والبلدية ونوع التوصيل و**`desk`** والبنود والمبالغ والكوبون و**كل مفاتيح `extra`** عدا «🔗 مرجع» و«🧺 مجموعة» (`VOLATILE`). ويُعاد الحساب عند الإرسال على الطلب **النهائي**.
- **الخادم (`submit_order` في Supabase وملف PHP):** قفل استشاري لكل مفتاح؛ `req_hash` = نفس الحقول بما فيها `desk` و`extra` عدا المتقلّبين. مفتاح موجود + بصمة مطابقة ⇒ يعيد رقم الطلب الأول؛ مفتاح موجود + بصمة مختلفة ⇒ `idempotency_key_reuse` (409 في PHP).
- **شبكة `duplicate_order`:** اختيارية (إعداد مكافحة الاحتيال، IP وساعات محددة) فلا يُعتمد عليها.

|---|---|---|---|---|
| **A (الحالي)** | العنوان في `extra` قبل `__ik` | آمن ✓ | **طلب ثانٍ** (مفتاح جديد) — ثغرة ضيقة | ✓ |

## 4) الاختبارات (`scripts/test-order-desk-idempotency.js`)
**الجزء 1 (شيفرة العميل الفعلية، بلا شبكة): 6/6.** O1 نفس الطلب ⇒ نفس المفتاح · O2 `__ik` = مفتاح الإرسال في A · O3 تغيّر العنوان ⇒ مفتاح مختلف (أثر A) · O4 B يكسر الاتساق · O5 وسم المجموعة والمرجع لا يغيّران المفتاح · O6 تغيّر `desk` يغيّر المفتاح دائماً.

**الجزء 2 (`submit_order` الحقيقي على `alyssum-beta` — دالة مطابقة حرفياً لنسخة هذا الفرع بعد توحيد الفراغات؛ طلبات اصطناعية حُذفت كلها):**
| الاختبار | النتيجة |
|---|---|
| R1 إعادة الإرسال ×3 بنفس المفتاح | معرّف واحد، **طلب واحد** ✓ |
| R2 12 إرسالاً **متزامناً** بنفس المفتاح | معرّف واحد للجميع، **طلب واحد** ✓ (القفل الاستشاري يسلسل) |
| R3 نفس المفتاح + عنوان مختلف | `idempotency_key_reuse` ولا طلب ثانٍ ✓ |
| R4 (A) تغيّر العنوان بين محاولتين (مفتاحان) | **FINDING:** يُنشأ طلبان (ثغرة ضيقة موثَّقة، ليست فشلاً) |

**إثبات C (بلا تغيير فعلي):** داخل معاملة مُرجَعة على Beta (التحقق بعد التنفيذ: 0 طلبات، 0 مفاتيح، الدالة سليمة): الدالة الحالية (شاهد) ⇒ `idempotency_key_reuse`؛ الدالة معدَّلة باستثناء `📍 عنوان المكتب` من البصمة ⇒ **المعرّف نفسه، طلب واحد، بلا خطأ**. وعلى العميل: إضافة العنوان إلى `VOLATILE` تجعل المفتاح ثابتاً مهما تغيّر نصه.

## 5) التوصية
1. **لا يُعتمد الدمج الحالي نهائياً بعد.** النتيجة المطلوبة (لا طلبات مكررة عند إعادة الإرسال والتزامن) **مُثبَتة للخيار A** في الحالات الواقعية (نفس الطلب).
2. الثغرة الوحيدة المتبقية (تغيّر نص العنوان بين محاولتين خلال 30 دقيقة، أي تحديث دليل المكاتب في تلك الدقائق) تُغلق بـ**C**: ثلاثة تعديلات صغيرة متزامنة: `VOLATILE` في `api.js`، واستثناء `- '📍 عنوان المكتب'` في `submit_order` (`platform/supabase/schema.sql`)، و`unset($ex['📍 عنوان المكتب'])` في `platform/php-edition/api/index.php`. **C يغيّر دالة SQL وملف PHP الإنتاجيين عند النشر، فلم أطبّقه.**
3. المطلوب منك: اعتماد A مؤقتاً، أو C (بنشر منسّق)، أو إبقاء 12B.1 خارج `main`.
