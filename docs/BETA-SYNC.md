# مزامنة Beta مع المنصة الأساسية (BETA-SYNC)

> **الحكم الصريح:** الآلية **مكتملة ومختبرة محلياً بمحاكيات صريحة**. **لم تُجرَّب على Cloudflare ولا Supabase ولا GitHub Actions الحقيقية**، ولا يجوز اعتبار الاختبارات المحلية دليلاً على نجاح التكامل الحقيقي. انتظار: إنشاء بيئة GitHub `alyssumdz-beta` وإدخال أسرارها (دليلها `docs/BETA-GITHUB-ENVIRONMENT.md`)، ثم تنفَّذ الاختبارات الحقيقية في §11. لا شيء نُشر على Production، ولا دمج في `main`.
> الحالات: `VERIFIED` أُثبت كما هو موصوف · `PARTIALLY VERIFIED` بمحاكاة فقط · `NOT TESTED` لم يُجرَّب.

## 1) المعمارية المعتمدة (قرار 2026-11-18)
**مصدر شيفرة واحد: `main`.** بيئتا تشغيل مستقلتان: **Production** و**Beta** (حساب Cloudflare ومشروع Supabase مستقلان لكل منهما). **الإصدار المعتمد يُنشر ويُختبر على Beta أولاً، ولا ينتقل إلى Production تلقائياً أبداً**: النشر إلى Production قرار بشري مستقل خارج هذه الآلية (تفرض السياسة W8 ألا يتسلسل أي workflow إنتاج معها، ولا تحوي أدواتها أي أمر Production).
الوضع الحالي (مرحلي): طبقة Beta (حارس البيئة، وحدة beta، أدوات النشر، الـWorker الساكن، هذه الآلية) تعيش على خط `beta/*` متأخر عن `main` **86 التزاماً** (قِيس: VERSION 1.89.1236 مقابل 1.89.1264، والدمج بلا تعارض). تحقيق المعمارية المعتمدة = **دمج طبقة Beta في `main`** (قرار منفصل بتفويضك؛ لم يُنفَّذ). حتى ذلك الحين: `sync-status` يقيس الفجوة، ودورة المزامنة: دمج `main` في خط Beta ← CI ← وسم اعتماد ← نشر.

## 2) تدفق الإصدار
```
commit معتمَد (على main أو موسوم beta-approved/<sha8>) · فاعل التشغيل ضمن BETA_APPROVERS
   │ CI: نجاح tests على الـSHA نفسه (لا تجاوز) · شجرة نظيفة تطابق الـSHA
   │ عقود التوافق · ترحيلات إضافية فقط · beta-content بيانات فقط ومعزول
   ▼
بناء الواجهة → بصمات (api/gateway/ui/templates) → بيان الإصدار
   ▼
لقطة بيانات (D1+Supabase) + نسخة صفوف D1 احتياطية (في KV الخاص بـBeta) ← قبل أي كتابة
   ▼
ترحيلات إضافية قابلة للاستئناف → api → gateway → ui → templates (ترتيب يحفظ توافق كل حالة وسيطة)
   │ فحص صحة بعد كل مكوّن · أي فشل ⇒ رجوع **الكود فقط**
   ▼
تحقق نهائي: هوية beta، مخطط، سلامة البيانات، دخان ← تسجيل الإصدار + التقرير
```

## 3) المكوّنات منفصلة الإصدار (متطلب 6)
`api` · `gateway` · `ui` (الواجهة + الـWorker الساكن) · `templates` (مسارات القوالب داخل الواجهة المبنية، مصدرها `contracts.json → template_prefixes` ويفحص الاختبار تطابقها مع الـWorker الساكن). لكل مكوّن بصمة ورقم `contract`؛ يُنشر **المتغيّر منها فقط**؛ `requires` و`min_ui/min_gateway` تُفحص ضد المنشور فعلاً؛ **ترتيب النشر يُحسَب** بحيث تبقى كل حالة وسيطة صالحة؛ كسر متزامن في الاتجاهين **مرفوض** (يُقسَّم إلى إصدارين).

## 4) استعادة D1 — الخطر والسياسة (متطلبان 3 و5)
**الخطر (مُثبَت بتجربة على الكود المدفوع `5ba628ea`):** كان المنسّق يستعيد D1 من علامة Time Travel عند فشل الترحيل أو فقدان البيانات. Beta حيّ؛ **طلب وصل بعد أخذ العلامة وقبل الفشل ضاع** (`status: failed_restored` والطلب غائب). الاستعادة بعلامة زمنية تمحو **كل** ما كُتب بعدها (طلبات وتحديثات وأحداث).
**السياسة الجديدة:** **لا استعادة تلقائية لقاعدة D1 أبداً** (لا دالة `restore` في المحوّلين، ويفحص الاختبار F0 عدم وجودها). بدلاً منها:
1. **الترحيلات قابلة للاستئناف:** فشل في المنتصف يُترك كما هو (إضافي) ويُكمَل بإعادة المحاولة؛ جملة `ADD COLUMN` لعمود موجود تُتخطّى. الكود القديم يعمل على التغيير الإضافي.
2. **رجوع الكود فقط** عند أي فشل؛ القاعدة تُوسَم صراحةً «لم تُمسّ».
3. **هوية الصفوف = المفتاح الأساسي المُعلَن** (بسيط أو مركّب)، لا `rowid` (يُعاد استعماله بعد الحذف فيُخفي الفقد؛ اكتُشف هذا العيب باختبار وصُحِّح).
4. **كشف الفقدان:** يفشل النشر عند **اختفاء أي مفتاح كان موجوداً**؛ الزيادة (كتابات المستخدمين أثناء النشر) مسموحة ولا تُنذر.
5. **استعادة جراحية يدوية غير مدمّرة:** `beta-release.mjs recover-missing --release <id> [--apply]` تعيد **الصفوف المفقودة وحدها** من النسخة الاحتياطية بـ`INSERT OR IGNORE` (لا تحذف ولا تعدّل أي صف موجود، ولا تمسّ الجديد؛ معاينة افتراضياً؛ إعادة التشغيل آمنة)، وتتطلب معتمِداً مُسمّى. الجداول الأكبر من 2000 صف بلا نسخة صفوف تُبلَّغ يدوية.
6. العلامة الزمنية تُسجَّل في التقرير للاستعمال **اليدوي** بقرار بشري فقط (تُضيّع ما بعدها).
نسخة الصفوف الاحتياطية في KV الخاص بـBeta وحده، **ولا تدخل التقارير ولا artifacts** (اختبار G9).

## 5) حماية بيانات Beta (متطلبان 4 و5)
لا نقل بين Production وBeta (حواجز في §8). النشر لا يمسّ البيانات: ترحيلات إضافية، واجهة محتوى معنوَن بالبصمة، Workers نسخ. **Supabase:** فقدان بياناته ⇒ رجوع الكود + **تنبيه صريح** بالجدول والمعرّفات المفقودة وأن الاستعادة **يدوية** من النسخة الاحتياطية للمشروع (لا علامة استعادة ولا استعادة D1 بسببه) — اختبار [28][29]. *حدّ:* لا نسخة صفوف لـSupabase (تُحفظ قوائم المعرّفات فقط).

## 6) الرجوع (متطلبان 4 و7)
Workers: نشرة نسخة سابقة. الواجهة والقوالب: كتابة مؤشر واحد (المحتوى غير قابل للتغيير). **الرجوع لا يمسّ البيانات ولا يعكس ترحيلاً إضافياً**، ويتحقق من أن لا مفتاح اختفى. اختُبر: بيانات وصلت **أثناء** النشر وبعده تبقى بعد الرجوع (G7–G8)، وطلب وصل أثناء ترحيل فاشل يبقى (G1–G2 وadapter [25]–[27])، وطلب وصل أثناء نشر api ثم فشلت الواجهة (G3). يتطلب معتمِداً مُسمّى.

## 7) سياسة الاعتماد (متطلب 7)
- **إلى Beta:** commit **اجتاز CI** على الـSHA نفسه (بلا تجاوز، و`--skip-gates` محظور مع deploy) **و**اعتماداً صريحاً: على `main` أو بوسم `beta-approved/<sha8>`، **وفاعل التشغيل ضمن `BETA_APPROVERS`** (إلزامي داخل Actions؛ فارغة = لا نشر). خارج Actions: `--approved-by <اسم>` إلزامي ويُسجَّل في البيان والتقرير. الرجوع والاستعادة الجراحية يتطلبان المعتمِد نفسه. بيئة `alyssumdz-beta` بمراجعين مطلوبين طبقة ثانية.
- **إلى Production:** لا يوجد مسار في هذه الآلية. قرار مستقل خارجها.
- فرضت السياسة W6r/W8 في `scripts/test-workflow-policy.py` (98 فحصاً، منها 12 سلبياً): وسوم `beta-approved/**` أو يدوي فقط، `contents: read`+`actions: read`، `needs: gate`، بيئة `alyssumdz-beta`، أسرار `BETA_*`، `--actor/--approvers` لكل نشر/رجوع، لا استدعاء مباشر لأدوات النشر/Cloudflare، لا دفع، ولا ربط مع workflows الإنتاج.

## 8) رفض موارد Production حتى عند خطأ الإعدادات (متطلب 6)
طبقات مستقلة: (1) المنشئ يرفض حساب Production المعروف، أي اسم Worker/D1/Worker ساكن يطابق Production، مضيفَي Beta إن كانا Production أو تحت `alyssumdz.com`/`alyssumhub.fyi`، ومرجع Supabase إنتاجي أو غير المسجَّل لـBeta؛ (2) **حارس النقل** يحظر قبل خروج أي طلب: أي حساب Cloudflare غير حساب Beta، وأي مشروع Supabase غير `alyssum-beta`، ومضيفي/مراجع/أسماء Production، وأي مضيف خارج Beta؛ (3) فحص نظافة الحساب (لا Worker/D1 بأسماء Production) قبل أي كتابة؛ (4) الواجهة ترفض `BETA_CF_ACCOUNT_ID` الإنتاجي و`BETA_SUPABASE_REF` الإنتاجي/المجهول وغياب المرجع بلا `--no-supabase` صريح، وسجلاً مُفسَداً — **قبل أي اتصال** (CLI [33]–[37]، adapter [31]–[37]). هوية قاعدة D1 `beta` تُفرَض قبل أي قراءة.

## 9) beta-content، التقرير، التشغيل
- `beta-content/`: بيانات متاجر Beta فقط، امتدادات `json md txt` وصور، بلا شيفرة، ولا ملف شيفرة في المنصة يقرأ منه (يُفحص في كل `verify`). *تطبيقه على متاجر Beta عبر API غير منفَّذ (يحتاج عقد API لإنشاء المتاجر).*
- التقرير: `beta-release/report-<id>.md` و`latest.md` و`result-<id>.json` (الـcommit، VERSION، السابق، CI، الاعتماد والمعتمِد، المكوّنات، الترحيلات والمُطبَّق، الخطوات، الرجوع، التنبيهات)، وعلى الموقع `/beta-release.json` وترويستا `X-Beta-Ui`/`X-Beta-Templates`، وعلى الـAPI `/health`.
- الأوامر: `sync-status | verify | plan | deploy | rollback | status | recover-missing`؛ ومن GitHub: `beta-release.yml` (`mode=deploy|rollback|status` أو وسم). التفاصيل والأسماء في `docs/BETA-GITHUB-ENVIRONMENT.md`.

## 11) الاختبار الحقيقي — لم يُنفَّذ بعد (ينتظر البيئة والأسرار)
بعد إنشاء البيئة وإدخال الأسرار تُنفَّذ بالترتيب، وتُسجَّل نتائجها هنا بأرقام تشغيل ومخرجات حقيقية، ولا يُعدّ أي بند ناجحاً إلا بها:
1. **GitHub Actions:** `beta-release` بـ`mode=status` (حارس نظافة الحساب، الصحة) ← يُثبت البيئة والأسرار والمعتمِدين.
2. **Cloudflare الحقيقي:** التحقق من مسارات `time_travel/bookmark` (للتسجيل اليدوي)، Workers Deployments/Versions، `/health` للـAPI والـgateway، KV (مؤشرات/كائنات)، `deploy.mjs --env beta worker` عبر المحوّل.
3. **Supabase الحقيقي:** لقطات الجداول المحمية بالـPAT، وصحة أعمدة المفاتيح في `contracts.json`.
4. **سيناريو إصلاح خطأ على Beta:** إصدار A (فيه الخطأ) ← إنشاء متجر وطلبات اصطناعية (D1 + طلب Supabase عبر `submit_order`) ← إصلاح + ترحيل إضافي + تغيير قالب ← اعتماد ونشر عبر workflow ← إثبات: الخطأ زال، المتجر والطلبات باقية (المعرّفات نفسها) ← رجوع إلى A ← إثبات بقاء البيانات (بما فيها ما أُنشئ بعد بدء النشر) ← تنظيف الصفوف الاصطناعية فقط.
5. **اختبار الاستعادة الجراحية حقيقياً** على صف اصطناعي حُذف عمداً.
**يتطلب كل ذلك تفويضك صراحةً عند التنفيذ** (وسم اعتماد، تشغيل workflow، كتابة بيانات اصطناعية في Beta).

## 12) ما لم يُجرَّب / قيود
Time Travel وWorkers Deployments وترويسات الصحة ومخرجات Supabase الحقيقية (NOT TESTED)؛ تشغيل الـworkflow؛ الأداء على نشرات كبيرة (حدود KV المجانية)؛ تطبيق beta-content على المتاجر؛ دمج طبقة Beta في `main` (المعمارية المعتمدة، ينتظر تفويضك)؛ نسخة صفوف لجداول أكبر من 2000 صف ولـSupabase؛ تحديثات (UPDATE) الصفوف أثناء النشر لا تُرصد (يُرصد الحذف/الاستبدال فقط).
