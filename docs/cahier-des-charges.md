# Cahier des charges — منصة «أليسوم» للتجارة الإلكترونية (SaaS على شاكلة Shopify)

> **الإصدار:** 1.0 — أكتوبر 2026 — مبني على: `docs/shopify-architecture-report.md` (تقنيات Shopify) و`docs/shopify-admin-modules.md` (27 وحدة لوحة التاجر) و`docs/roadmap.md`، ومقابَل بما أُنجز فعلاً في المستودع حتى النسخة 1.70.0.
> **الغاية:** وثيقة مرجعية واحدة تحدّد ما نبنيه، لمن، بأي معمارية، بأي أولوية، وكيف نقبل التسليم. يرجع إليها Claude وCodex وأي مطوّر جديد قبل أي عمل على المنصة.
> **اللغة:** العربية أولاً (RTL) مع مصطلحات تقنية فرنسية/إنجليزية كما هي.

## 1. Contexte et objectifs — السياق والأهداف

### 1.1 السياق
- متجر «أليسوم» (alyssumdz.com) متجر جزائري للمنتجات الطبيعية، موقع ثابت على GitHub Pages، بدفع عند الاستلام وتوصيل لكل الولايات.
- تطوّر المتجر من موقع بسيط إلى **لوحة تحكم كاملة + منشئ صفحات + أدوات تسويق وتوصيل**، وأصبح ممكناً بيعه/تأجيره لتجّار آخرين كمنصة.
- مرجعنا الوظيفي هو Shopify، **لا نقلّدها تقنياً** بل نبني نسخة أصغر بكثير، مناسبة للسوق الجزائري (COD، Yalidine وأخواتها، واتساب، 69 ولاية، العربية).

### 1.2 الأهداف
| # | الهدف | مؤشر النجاح |
|---|---|---|
| O1 | تاجر واحد يدير متجره كاملاً من لوحة واحدة دون أدوات خارجية | يغطي المتطلبات الأساسية (§5) بنسبة ≥ 90% |
| O2 | أي تاجر جديد يُطلق متجراً في أقل من ساعة | معالج «تجهيز المتجر» + قالب جاهز + استيراد منتجات CSV |
| O3 | نفس الكود يعمل على **ثلاث خلفيات** دون تعديل | GitHub/Supabase، نسخة PHP، الوضع المحلي (§4.2) |
| O4 | منصة متعددة المتاجر (Multi-tenant) آمنة | عزل بيانات كامل بـ`store_id` + RLS (§4.3) |
| O5 | قابلية التوسع بتطبيقات وإضافات | نظام Extensions + Webhooks + API (§8) |
| O6 | هوية بصرية موحّدة واحترافية | نظام تصميم «الزجاج الداكن» (§9) |

### 1.3 خارج النطاق (حالياً)
نقاط البيع POS، المتجر متعدد العملات/اللغات الكامل، متجر تطبيقات عام، تطبيق موبايل أصلي (يُكتفى بـPWA)، الدفع الإلكتروني المباشر (CIB/Edahabia/Chargily) قبل المرحلة 4 (القرار في §5.13)، تنفيذ إعلانات Meta عبر Marketing API.

## 4. Architecture cible — المعمارية

### 4.1 الطبقات
```
┌────────── Admin (admin.html + وحدات JS) ──────────┐   ┌─── Storefront (HTML/CSS/JS ثابت) ───┐
│  نظام تصميم «الزجاج الداكن»، Ctrl+K، RBAC          │   │  صفحات منتج/رئيسية/فئات/سلة/حساب/PWA │
└───────────────┬────────────────────────────────────┘   └───────────────┬─────────────────────┘
                └───────────────  طبقة API موحّدة (API.*)  ───────────────┘
        ┌───────────────┬──────────────────────┬────────────────────────────┐
        │ github        │ sb (Supabase)         │ php (SQLite + api/index.php)│
        │ ملفات JSON/JS │ Auth+Postgres+RLS+Storage │ نسخة استضافة منفردة      │
        └───────────────┴──────────────────────┴────────────────────────────┘
```

### 4.2 قيد التوافق وحدوده (إلزامي لكل ميزة)
كل ميزة تعمل على **الأنظمة الثلاثة** دون تغيير منطقها: `GitHub Pages (+Supabase/Apps Script)` · `نسخة PHP (CONFIG.BACKEND="php")` · `الوضع المحلي`. البيانات تُكتب عبر `Admin.publishDataJs()` / `GH.putFile` / `PHPAPI` فقط؛ **ممنوع** نداء Supabase أو Apps Script مباشرة من كود جديد، و**ممنوع** وضع `service_role` أو أي مفتاح في المستودع.

> **توضيح واقعي:** «نفس الكود على ثلاث خلفيات» تعني **نفس واجهة المتجر واللوحة ونفس عقد البيانات**، لا نفس مستوى الضمان الأمني. GitHub Pages ملفات ثابتة **لا تفرض أي تحقق**؛ التحقق الملزم لا يوجد إلا حيث توجد شيفرة خادم.

#### 4.2.1 أين يجري التحقق الفعلي ومصدر الحقيقة (قرار — **هدف التنفيذ؛ غير منجز بعد**، يُنفَّذ ضمن FR-SHP-5 والمرحلة 3)
| الخلفية | تحقق الشحن/الخصم/المخزون | مصدر الحقيقة للسعر | للمخزون | لاستعمال الكوبون | الضمان |
|---|---|---|---|---|---|
| **Supabase** (الموصى بها) | دالة قاعدة بيانات/Edge `place_order` تُعيد الحساب كاملاً من جداول الخادم | `products` + `shipping_zones` + `discounts` في Postgres | `stock` في Postgres بخصم ذرّي داخل معاملة | جدول `coupon_uses` مع قيد فريد + `SELECT … FOR UPDATE` | **ملزم** |
| **PHP** (استضافة) | `api/index.php` يُعيد الحساب من ملفات/SQLite المنشورة | `data.js`/`wilayas.js` على الخادم (يقرؤها PHP) + `coupons.json` | SQLite بمعاملة | جدول SQLite بقيد فريد ومعاملة `BEGIN IMMEDIATE` | **ملزم** |
| **GitHub Pages + Apps Script** | Apps Script يُعيد التحقق (`LockService`) إن نُشر | ملفات المستودع المنشورة | غير ذرّي بين مواقع؛ حدّ إرشادي | `LockService` على الورقة | **جزئي** |
| **محلي** | لا خادم | — | — | — | **للتجربة فقط، لا أمان** |
- **قاعدة:** المتصفح يرسل **المعرّفات والكميات والكوبون فقط** (slug، variant، qty، code، wilaya، commune، dtype)؛ الخادم يحسب المجاميع ويُرجع المبلغ المعتمد، وأي مبلغ يرسله المتصفح يُتجاهل ويُسجَّل الفرق كتنبيه.
- **حد التوافق:** ميزة تتطلب تحققاً ملزماً (الكوبون ذو حدّ استعمال، الدفع، مخزون ذرّي) تُعلَّم في اللوحة «تتطلب خلفية خادمية» وتُعطَّل أو تعمل إرشادياً على GitHub Pages البحتة.

### 4.3 تعدد المتاجر (Multi-tenant) — المرحلة 4
- كل جدول يحمل `store_id` مع سياسات RLS؛ جداول: `stores, store_users(role), products, variants, orders, order_items, customers, pages, files, discounts, shipping_zones, events, webhooks, apps`.
- نموذج النشر الحالي (كل متجر = مستودع/استضافة بنسخة من الكود) **يبقى مدعوماً**؛ التعدد على Supabase خيار إضافي.
- التحديث عن بُعد لمواقع الزبائن قائم (`shared-files.json`, `release.py`) ويستمر.

### 4.4 البيانات الحالية
| المجال | مكان التخزين |
|---|---|
| المنتجات | `assets/js/data.js` |
| الولايات/المناطق/البلديات | `assets/js/wilayas.js` (`WILAYAS` + `SHIPPING`) |
| الطلبات | Google Sheets (Apps Script) أو Supabase أو SQLite (PHP) |
| إعدادات | `assets/data/*.json` (coupons, inventory, customers, social, notify, theme…) |
| صفحات | `assets/pages/*.json` + `_conv/` |

## 5. Exigences fonctionnelles détaillées — المتطلبات الوظيفية

> الأولوية: **P0** أساسي · **P1** مهم · **P2** توسّع. معيار القبول (AC) يُختبر بمتصفح حقيقي (Playwright).

### 5.1 الطلبات والدفع (P0)
- **FR-ORD-1** طلب سريع من صفحة المنتج والسلة بدفع عند الاستلام؛ تحقق هاتف جزائري؛ حقول إضافية مخصّصة.
- **FR-ORD-2** حالات: `new → confirmee → expediee → livree` و`echec | annulee`؛ تغيّرها يطلق: خصم/إعادة مخزون، إشعار واتساب، إدراج القائمة السوداء عند الفشل.
- **FR-ORD-3** إرسال إلى شركة التوصيل مع تتبّع؛ الولايات 59–69 تُرسل باسم الأم (§5.14).
- **FR-ORD-4** عروض محفوظة، إجراءات جماعية (حالة، نسخ أرقام، تصدير).
- **FR-ORD-5 (P2)** فاتورة PDF وملاحظات داخلية وسجلّ زمني (Timeline) للطلب.
- **AC:** طلب تجريبي ينتقل بين الحالات فيتغيّر المخزون والإشعار وسجلّ الشركة مرة واحدة لكل انتقال.

### 5.2 المنتجات (P0)
- عنوان/وصف/صور/فيديو/سعر/سعر قديم/وسوم/فئات/متغيّرات/عروض كمية/شحن مجاني حسب المنتج.
- تعديل جماعي (7 حقول) مع معاينة قبل/بعد واستيراد/تصدير CSV بمطابقة `slug`.
- **فحص جودة** (درجة /100) للصور والوصف والأسعار والروابط.
- **FR-PRD-4 (P1)** حقل سعر التكلفة ووحدة SKU/Barcode وSEO لكل منتج (Meta title/description/slug).
- **FR-PRD-5 (P2)** Metafields مرنة لكل متجر.

### 5.3 المخزون (P0/P1)
- كمية لكل منتج/متغيّر، حدّ منخفض، خصم تلقائي عند التأكيد وإعادة عند الإلغاء/الفشل، استيراد/تصدير CSV.
- **FR-INV-4 (P2)** Locations متعددة ونقل مخزون وجرد.

### 5.4 المرتجعات والاسترداد (🟠 مهمة، P1) — *قيد التنفيذ (Codex E)*
- **من يطلب؟** التاجر وحده يفتح طلب الإرجاع من اللوحة (زبون ← واتساب/مكالمة)؛ لا بوابة ذاتية للزبون الآن. يصحّ فقط لطلب **سُلِّم** (`livree`) وخلال مهلة قابلة للضبط (افتراضي 14 يوماً من التسليم).
- **السجل:** `{id, orderId, items:[{sku/slug, qty, reason}], kind: return|exchange|refund, status, amount, restock, restocked, createdAt, receivedAt}`.
- **الحالات المسموحة (انتقال أحادي الاتجاه):** `requested → approved|rejected`؛ `approved → received` (استلام المنتج فعلياً)؛ `received → refunded|exchanged|closed`. لا رجوع للخلف؛ `rejected/closed/refunded/exchanged` نهائية.
- **التمييز بين ثلاثة أحداث منفصلة:** (1) **طلب الإرجاع** `requested` — لا يغيّر مخزوناً ولا مالاً؛ (2) **استلام المنتج** `received` — الحدث الوحيد الذي يسمح بإعادة المخزون (`restock:true` لقطع سليمة؛ التالفة `restock:false` فلا تُضاف للمخزون)؛ (3) **الاسترداد/الاستبدال** — الحدث المالي.
- **حساب المبلغ:** استرداد كامل = مجموع قيم الأصناف المرتجعة (بسعرها وقت الطلب بعد حصتها من الخصم) + الشحن فقط إن كان الخطأ من المتجر (خيار `refundShipping`)؛ **جزئي** = كميات أقل من كمية الطلب (كل صنف ≤ المتبقّي غير المُرتجع سابقاً)؛ **استبدال** = صنف بديل بفرق سعر موجب (يُحصَّل) أو سالب (يُسترد)؛ المبلغ يُقرَّب للدينار ولا يتجاوز مبلغ الطلب.
- **AC:** (أ) إعادة المخزون **مرة واحدة** لكل سطر حتى لو كُرِّر حدث `received` أو أُعيد إرسال الطلب (`restocked` علم لكل سطر). (ب) لا يمكن تسجيل كمية مرتجعة تتجاوز المتبقّي. (ج) طلب غير مسلَّم يرفض فتح إرجاع. (د) الاسترداد يظهر في المالية/التقارير مرة واحدة. (هـ) قطعة تالفة `restock:false` لا تغيّر `stock`.

### 5.5 العملاء (P1)
- تجميع بالهاتف المطبَّع، شرائح (جديد/متكرر/VIP/خامل/مخاطرة)، وسوم وملاحظات، واتساب، تصدير CSV. حسابات زبائن + طلبات سابقة + هدية ترحيب.
- **FR-CUS-4 (P2)** شرائح يحدّدها التاجر بشروط، واستيراد عملاء.

### 5.6 الخصومات (P0)
- كوبون نسبة/مبلغ/شحن مجاني/هدية، حدّ أدنى، فترة، حدّ استعمال، مرة لكل هاتف، أول طلب، فئات/منتجات مؤهلة، الجمع مع عرض الكمية. رسائل رفض عربية دقيقة.
- **FR-DSC-3 (P1)** Buy X Get Y، خصم تلقائي بلا كود.
- **ملاحظة أمان:** عدّاد الاستعمال الكلي إرشادي حالياً → يلزم فحص خادم (§6.1).

### 5.7 التوصيل (🟠 مهمة → P0 للمنجز) — **مناطق التوصيل Zones** (أُنجز v1.67–1.70)
- مناطق مرقّمة، لكل منها **سعر منزل وسعر مكتب**، **شحن مجاني** (دائماً أو عند مبلغ)، وقائمة ولايات.
- **«التوصيل غير متوفر» لكل منطقة:** بلديات أو ولايات كاملة، بنوعين `all|home`.
- الولايات الـ**69** (منها 59–69 الجديدة بـ108 بلدية) وتوافق الشركات القديمة عبر `par`.
- **FR-SHP-5 (P0)** تحقق **على الخادم** من سعر الشحن والاستثناءات (حالياً في المتصفح فقط).
- **FR-SHP-6 (P1)** استيراد/تصدير المناطق CSV، وقوالب مناطق جاهزة.
- **FR-SHP-7 (P1)** تحديث أرقام الولايات بعد 31/12/2026 عند تحويل الشركات للنظام الجديد (مفتاح `par` يُعطَّل).

### 5.8 المتجر والمحرّر (Store Builder) — 🔴 وحدة رئيسية (P0)
- منشئ صفحات مرئي (عناصر حرة، أقسام، أجهزة، حركات، تأثيرات)، 17 قالب متجر + نماذج، تثبيت قالب على الرئيسية والمنتجات، نسخ قالب من موقع/صورة، مولّد صور.
- **FR-STO-3 (P0)** Store Builder وحدة قائمة بذاتها في اللوحة (أول قسم «المتجر»): صفحات، ثيم، هيدر/فوتر، عناوين، نطاق، SEO، ووسائط في مكان واحد.
- **FR-STO-4 (P1)** إدارة **Navigation/Menus** مستقلة، **Blog** (مقالات)، صفحات السياسات.
- **FR-STO-5 (P1)** SEO: sitemap، robots، بيانات منظّمة JSON-LD للمنتج، Open Graph.
- **FR-STO-6 (P2)** نطاق مخصص بخطوات إرشادية، وتغيير الخط/الألوان على مستوى الثيم.

### 5.9 التسويق (P1)
- جدولة منشورات FB/IG بعدد يومي وقوالب نصية ومولّد مسودات؛ حملات إعلانية (UTM، CPC/CTR/CPA/ROAS، نسب الطلبات).
- بكسلات (Meta/TikTok/…) وتتبع الحملات في الطلب.
- **FR-MKT-3 (P1)** سلات متروكة (Abandoned carts) باسترجاع واتساب.
- **FR-MKT-4 (P2)** حملات واتساب/SMS مجدولة، Email marketing، إنشاء إعلانات عبر Marketing API.

### 5.10 التحليلات والتقارير (P1)
- الرئيسية، التحليلات، المالية (ربح صافٍ بعد التوصيل والمرتجع والإعلان)، التقارير المتقدمة (فترة مخصصة، مقارنة، فئة، ولاية، حملة، قمع).
- **FR-ANA-4 (P1)** Live View وبطاقات Insights تلقائية في الرئيسية (اتجاهات المبيعات، منتج تراجع، ولاية ترتفع، مخزون ينفد).
- **FR-ANA-3 (P2)** معدل التحويل (زيارات ← سلة ← طلب) ومصادر الزيارات، وتقارير مخصصة محفوظة.

### 5.11 الأتمتة (Flow) (🟡 توسّع، P2)
- محرّك قواعد: `Trigger → Condition → Action` (مثال: «طلب > 50000 دج ← وسم VIP»، «مخزون < 5 ← إشعار»، «الطلب الخامس ← وسم»).
- محفّزات: `order.created/status_changed`, `inventory.low`, `customer.created`. إجراءات: وسم، إشعار واتساب، تغيير حالة، إرسال Webhook.
- **AC:** قاعدة تُنشأ بالواجهة وتُنفَّذ مرة واحدة لكل حدث وتُسجَّل في سجلّ.

### 5.12 الصلاحيات والفريق (🟡 توسّع، P2 — لكنها شرط المرحلة 4 SaaS)
- دعوة موظف، دور، صلاحيات لكل مجموعة، سجلّ نشاط (Audit log)، إنهاء جلسات. **تُفرض خادمياً.**

### 5.13 الدفع (🟠 مهمة) — **قرار: COD الآن، البوابات المحلية لاحقاً**
- **المرحلة 3 (المطلوب الآن، P1):** **الدفع عند الاستلام (COD) فقط** + حقل **حالة الدفع** للطلب يدوي (`unpaid | paid | refunded`) يُحدَّث من اللوحة ويظهر في التقارير والمالية. لا بوابة دفع.
- **المرحلة 4 (P2):** بوابات الدفع المحلية (CIB/Edahabia/Chargily) كـ**إضافات** (§8) — **بشرط** وجود تحقق خادمي (Supabase Edge أو PHP): الدفع يحتاج إنشاء جلسة دفع وWebhook تأكيد موقَّع لا يمكن لصفحة ثابتة فعله. على نسخة GitHub Pages البحتة (بلا خلفية) تبقى COD فقط.
- **AC:** تغيير حالة الدفع لا يغيّر حالة الشحن؛ استرداد (`refunded`) لا يُسجَّل إلا لطلب `paid` أو مسلَّم ويظهر في المالية مرة واحدة.

### 5.14 توافق التوصيل مع النظام الإداري الجديد (P0، منجز)
ولايات 59–69 تأخذ سعر/منطقة أمّها، وتُرسَل للشركات (`Admin.coOrder/wCo`) باسم الأم مع بلدية بتهجئة الشركة؛ المرجع: قانون 26-06 ومرسوم 26-206.

### 5.15 المساعد الذكي (🟡 توسّع، P1 للزبون/P2 للتاجر)
- للزبون: وكيل يجيب عن الأسعار/التوصيل/الطلب. للتاجر: «اسألني» (مقالات + شرح الإعدادات).
- **FR-AI-3 (P2)** مساعد تنفيذي («أنشئ خصم 20%»، «حلّل مبيعات الشهر») بصلاحيات محدودة وتأكيد قبل أي كتابة. **كل استدعاء Gemini/API خارجي مطفأ افتراضياً** (`CONFIG.AI_API=false`) ويُفعَّل بقرار المالك.

### 5.16 المالية (🟡 توسّع، P2)

## 6. Exigences non fonctionnelles — المتطلبات غير الوظيفية

### 6.1 الأمان
- **لا أسرار في المستودع** (رموز Meta في `localStorage`، مفاتيح الشركات في الخادم/إعدادات خاصة). لا `service_role`.
- التحقق الحاسم (أسعار الشحن، الخصومات، حدود الاستعمال، الصلاحيات، حالة المخزون) **على الخادم**؛ المتصفح للتجربة فقط.
- RLS على كل الجداول؛ تحديد معدل الطلبات وحماية الطلبات الوهمية (Guard) وقائمة سوداء.
- **معايير قبول أمنية قابلة للاختبار (على Supabase وPHP):**
  1. **الشحن:** تعديل سعر الشحن أو منطقة الولاية في JS المتصفح (أو في جسم الطلب) لا يغيّر المبلغ الذي يقبله الخادم؛ الطلب المخالف يُقبل بالمبلغ الصحيح أو يُرفض برمز `price_mismatch`.
  2. **الاستثناءات:** طلب لبلدية مستثناة (`all`) أو توصيل منزلي لبلدية `home` يُرفض خادمياً حتى لو عُدّل DOM.
  3. **الكوبون:** تغيير قيمة الكوبون/نسبته في المتصفح لا يؤثر؛ الخادم يقرأها من تعريفه ويتحقق من الحد الأدنى والفترة والفئات والجمع.
  4. **التزامن:** طلبان متزامنان بكوبون `limit=1` ينجح أحدهما فقط (الآخر `coupon_exhausted`)؛ و`perPhone` كذلك.
  5. **التكرار (idempotency):** إعادة إرسال الطلب نفسه (نفس `client_request_id`) لا تنشئ طلباً ثانياً ولا تستهلك كوبوناً ثانياً.
  6. **المخزون:** تزامن طلبين على آخر قطعة ينجح أحدهما ويرفض الآخر `out_of_stock`؛ تكرار انتقال الحالة (`confirmee` مرتين) لا يخصم مرتين، وتكرار `echec/annulee` لا يعيد المخزون مرتين.
  7. **الصلاحيات:** نداء كتابة بلا جلسة/دور كافٍ يُرفض 401/403 (RLS) ولا يتغير أي صف.
- ترميز كل نص من البيانات (`esc`/`textContent`) منعاً لـXSS؛ سياسة CSP للمتجر.
- نسخ احتياطي دوري لملفات البيانات والطلبات.

### 6.2 الأداء
- صفحة المنتج: LCP ≤ 2.5s على 4G، صور WebP ومتغيّرات مصغّرة، تحميل كسول، بلا مكتبات ثقيلة في المسار الحرج.
- اللوحة: فتح ≤ 3s، قوائم > 1000 صف بترقيم/افتراضية، حفظ دفعي (commit واحد للصور/البيانات).

### 6.3 التوافق والإتاحة
- RTL كامل، العربية أولاً والفرنسية ثانياً، أجهزة مكتب/تابلت/جوال، تباين ألوان ≥ 4.5:1، تنقل بلوحة المفاتيح، `aria` للنوافذ والقوائم.
- متصفحات: Chrome/Edge/Safari/Firefox الحديثة. وضع غير متصل جزئي للـPWA.

### 6.4 قابلية الصيانة
- كل أداة في ملف JS مستقل مسجَّل في `shared-files.json` + مدخل في `admin-help.json` + ملاحظة في `CLAUDE.md`.
- لا تكرار: قبل أي أداة يُبحث في `admin.html` عن الميزة الموجودة ويُطوَّر ما لزم (دروس v1.66).
- ترقيم: كل إصدار يرفع `VERSION` ويشغّل `scripts/build-admin-pb.py` ويُتحقَّق من `alyssumdz.com/VERSION`.

### 6.5 الموثوقية
- فشل أي استدعاء خارجي (Meta، شركة التوصيل) لا يُسقط الطلب؛ إعادة محاولة وسجلّ أخطاء واضح للتاجر.
- كل كتابة جماعية قابلة للتراجع أو معاينة قبلها.

## 7. Modèle d'événements — نظام الأحداث

## 8. API et extensibilité — الواجهات والإضافات

- **API-first (المرحلة 4):** `admin.html` عميل لواجهة موحّدة `/api/v1/{resource}` (REST بسيط أولاً، GraphQL لاحقاً) بمصادقة JWT وصلاحيات.
- **Extensions:** نقاط توسعة ثابتة مسجَّلة: `admin.nav`, `admin.dashboard.card`, `order.action`, `product.tab`, `checkout.field`, `storefront.block` (عناصر `PB.WIDGETS`)، `shipping.rate`, `discount.rule`, `payment.method`.
- **بيان الإضافة (manifest):** `{id, name, version, permissions[], extensions[], settings schema}` وتشغيل المنطق غير الموثوق في **صندوق رمل** (iframe sandbox / Worker)، لا وصول مباشر للمفاتيح.
- **Metafields/Metaobjects:** حقول مخصصة لكل متجر دون تعديل المخطط.
- أدوات المطوّر: CLI بسيط (`create-extension`, `deploy`) ووثائق مع أمثلة.

## 9. Design system — نظام التصميم

- هوية «**الزجاج الداكن الأخضر**» (مرجع: `docs/dashboard-design-reference.md`): شريط جانبي زجاجي، بطاقات إحصاء ملوّنة، مخططات خضراء، جداول بشارات حالة.

- **الأسطح العائمة** (نافذة/قائمة/لوحة) بخلفية معتمة صريحة `rgba(9,24,18,.985)`.
- **بلا إيموجي** في الواجهة الجديدة؛ أيقونات عصرية SVG موحّدة.
- مكوّنات أولية: Button, Card, Table, Form, Modal, Drawer, Toast, Tabs, Badge, EmptyState, Chart (ألوان فئوية مُتحقَّق منها بأداة `validate_palette`).
- مرجع الفلسفة: Polaris (اتساق، كثافة معلومات، سلوك متوقع) لا شكلها.
