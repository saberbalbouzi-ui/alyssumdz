# خطة الاستضافة متعددة المستأجرين (على نهج Shopify)

> قرار صاحب المتجر: دومين **جديد** مخصص للمنصة على Cloudflare، ويبقى `alyssumdz.com` (Hostinger → GitHub Pages) كما هو دون أي مسّ.
> الحالة: **الكود جاهز ومُختبر محلياً (بمحاكاة)، بانتظار حساب Cloudflare + دومين المنصة + `CF_API_TOKEN`.** لم يُنشر شيء على Cloudflare. البنود «⚠ للتحقق» ما زالت غير مراجَعة.

## 1) المشكلة
- كل زبون = مستودع GitHub Pages مستقل: دومين واحد لكل مستودع، وشهادة SSL تُضبط يدوياً، ولا يتوسع.
- المطلوب: زبون يربط دومينه (أو يحصل على اسم فرعي من المنصة) فيعمل موقعه بشهادة تلقائية، دون تدخل يدوي منا.

## 2) المبدأ
استضافة واحدة تستقبل **كل** الدومينات، وتحدّد الزبون من اسم المضيف (`Host`):

```
زائر ──► دومين الزبون (CNAME) ──► Cloudflare (شهادة تلقائية، Custom Hostname)
                                    │
                                    ▼
                         Worker واحد «موزّع المستأجرين»
                         1) يقرأ Host   2) يبحث عنه في Supabase (saas_sites)
                         3) يجلب محتوى موقع الزبون من مصدره (المرحلة 1: مستودعه)
                         4) يخزّن مؤقتاً (cache) ويعيد الصفحة
```

- **دومين المنصة (جديد، يُشترى):** منطقة (zone) في Cloudflare. فيه `*.دومين-المنصة` للأسماء الفرعية (`اسم.دومين-المنصة`) و`مضيف التحويل` (fallback origin) الذي يوجّه إليه الزبائن بـCNAME.
- **دومين الزبون:** يضع الزبون سجل `CNAME` واحداً نحو مضيف التحويل (دومين فرعي)، أو سجلات A/CNAME حسب ما يعطيه Cloudflare لدومين الجذر. الشهادة تُصدَر وتتجدد تلقائياً.
- قاعدة البيانات والدوال تبقى على Supabase كما هي.

## 3) المراحل

| المرحلة | المحتوى | القبول |
|---|---|---|
| 0 | شراء دومين المنصة، نقل DNS له إلى Cloudflare، سرّ `CF_API_TOKEN` | المنطقة «نشطة»؛ `*.دومين` يردّ عبر Cloudflare |
| 1 | **الجسر:** Worker يوزّع بحسب `Host` ← `saas_sites` ← مصدر الموقع (مستودع الزبون الحالي). موقع تجريبي واحد | زيارة `تجربة.دومين-المنصة` تعرض الموقع بشهادة صحيحة؛ مضيف غير معروف يعرض صفحة «غير موجود» |
| 2 | **ربط الدومين برمجياً:** Edge Function `domains` (Supabase) تُنشئ/تفحص/تحذف Custom Hostname عبر Cloudflare API؛ أعمدة جديدة في `saas_sites`؛ بطاقة اللوحة تعرض حالة DNS والشهادة وتعليمات الـCNAME | زبون تجريبي يربط دومينه فيعمل بـHTTPS دون تدخلنا |
| 3 | **شراء الدومينات** (امتدادات عالمية) من اللوحة عبر API المسجِّل (Hostinger أو غيره بعد التحقق) بموافقة لكل عملية وعرض السعر قبل الدفع | شراء `.com` تجريبي وضبط DNS تلقائياً |
| 4 | نقل المحتوى من مستودع لكل زبون إلى مخزن مركزي (R2/Storage)؛ الزبائن الجدد عليه مباشرة | الموقع الجديد يعمل بلا مستودع |

الزبائن القدامى يبقون على GitHub Pages حتى تكتمل المرحلة 4؛ لا انقطاع.

## 4) تغييرات البيانات (مقترحة، تُضاف إلى `saas/schema.sql`)
- `saas_sites`: `host text unique` (الاسم الفرعي أو الدومين الفعّال)، `source text` (مصدر المحتوى)، `cf_hostname_id text`، `cf_status text`، `ssl_status text`، `cf_checked_at timestamptz`.
- دالة `saas_site_by_host(p_host)` (تُقرأ من الـWorker، تُرجع `source` والحالة ولا شيء آخر).
- ما يخص الإغلاق والاشتراك (`suspended`…) يطبّقه الـWorker من الحالة نفسها فلا يحتاج منطقاً جديداً.

## 5) الأسرار (تُوضع في بيئة/Secrets، لا في المستودع ولا في المحادثة)
- `CF_API_TOKEN`، `CF_ZONE_ID`، `CF_ACCOUNT_ID` — Supabase Edge Functions Secrets (لدالة `domains`).
- أسرار الـWorker في Cloudflare (قراءة `saas_site_by_host` بمفتاح عام فقط).
- `HOSTINGER_API_TOKEN` — فقط إن اعتُمد Hostinger لشراء الدومينات (المرحلة 3).

## 6) ما لا يمكن أتمتته
- **`.dz`**: يديره NIC.DZ بوثائق قانونية؛ لا API عالمي. الزبون يشتريه من مسجِّل محلي ثم يضع CNAME عندنا. لا نعد الزبائن بشراء `.dz` من اللوحة.
- **الدفع**: الطرق المتاحة لدى صاحب المتجر RedotPay (فيزا دولية) وPayPal. البطاقات المحلية غير مقبولة في الخدمات العالمية.

## 7) الأرقام (تحقق منها من توثيق Cloudflare الرسمي، أكتوبر 2026)
- **Cloudflare for SaaS (Custom Hostnames):** متاح في الخطة المجانية؛ **100 مضيف مشمول**، ثم **0.10$ لكل مضيف إضافي شهرياً**، حدّ أقصى 50,000. (المضيفات البدل wildcard والشهادات المخصصة وmTLS: Enterprise فقط — لا نحتاجها.)
- **Workers المجانية:** 100,000 طلب/يوم، 10ms CPU، 50 طلباً فرعياً لكل طلب. المدفوعة: 10 ملايين طلب/شهر مشمولة ثم 0.30$ لكل مليون إضافي. طلبات الملفات الثابتة (Static Assets) مجانية وغير محدودة.
  - **أثر عملي:** مئات المواقع ستتجاوز 100 ألف طلب/يوم قريباً ← خطة Workers المدفوعة (حوالي 5$/شهر) مطلوبة عملياً من المرحلة 1 فصاعداً. ولهذا سبب إضافي لنقل المحتوى إلى Static Assets/تخزين مركزي (المرحلة 4).
- **ما زال ⚠ للتحقق:** (1) هل يلزم حفظ وسيلة دفع في الحساب لتفعيل Custom Hostnames المجاني؛ (2) قبول Cloudflare لبطاقة RedotPay/PayPal؛ (3) شروط GitHub Pages لتمرير الطلبات عبر وكيل وحدود المعدل مع آلاف المواقع؛ (4) أداء الاتصال من الجزائر؛ (5) توفر اسم الدومين الجديد.

## 7-ب) إعداد Cloudflare (تأكد من التوثيق الرسمي، ديسمبر 2026)
1. أضف دومين المنصة إلى Cloudflare على الخطة **Free**، ثم فعّل Cloudflare for SaaS عليه (SSL/TLS ← Custom Hostnames).
2. المضيف الاحتياطي (fallback origin) يجب أن يكون سجلاً **Proxied بلا خادم أصل**: `service.<المنصة> AAAA 100::`، ثم يُعيَّن كـFallback Origin وتُنتظر حالته Active.
3. مسار الـWorker: `*/*` على المنطقة (يلتقط الدومينات المخصصة وأسماء المنصة الفرعية معاً، ولا حاجة لمسار لكل زبون).
4. لا يُنشأ Custom Hostname يطابق اسم المنطقة نفسها.
5. الدومين المخصص للزبون يُوجَّه بـCNAME إلى `service.<المنصة>`.
6. حدّ الدومينات 50,000 على كل الخطط، و100 مجاناً ثم 0.10$ لكل دومين.

## 8) المخاطر
- الاعتماد على مصدر GitHub في المرحلة 1 (حدود/شروط) ← نقل مبكّر للمحتوى المركزي.
- خطأ في الموزّع يؤثر على كل الزبائن ← بيئة تجريبية ونشر تدريجي، وصفحة تراجع.
- أي خلل في ربط الدومين لا يجب أن يمسّ `alyssumdz.com` (منطقة منفصلة تماماً).

## 9) المطلوب من صاحب المتجر
1. شراء دومين المنصة (من Hostinger أو غيره) وإخباري باسمه.
2. حساب Cloudflare مجاني، وإضافة الدومين إليه، وتغيير الـNameservers عند المسجِّل.
3. وضع `CF_API_TOKEN` (صلاحيات: DNS وSSL/Custom Hostnames لتلك المنطقة فقط) في الأسرار، وعدم لصقه في المحادثة.

## 10) ما أُنجز في المستودع
- `saas/schema.sql` القسم 10 (**طُبّق على المشروع الحقيقي واختُبر بدور anon**): أعمدة `host/source/cf_hostname_id/cf_status/ssl_status/cf_checked_at` في `saas_sites`، وفهارس فريدة للمضيف والاسم الفرعي، والدالة `saas_site_by_host(p_host, p_sub)` (تُرجع الحالة والمصدر فقط).
- `saas/worker/tenant-router.js` + `wrangler.toml`: الموزّع (اختُبر بمحاكاة: توجيه، إعادة كتابة التحويلات، مضيف مجهول 404، موقف 503، منع غير GET، حجب `set-cookie`). **`PLATFORM_DOMAIN` ما زال `CHANGE-ME.example`.** مستودعات الزبائن التي فيها ملف `CNAME` تحوّل `github.io` إلى دومينها، فيجب إزالة `CNAME` منها قبل اعتمادها كمصدر.
- `saas/functions/domains/index.ts`: ربط/فحص/إزالة Custom Hostname (للمدير فقط، يتحقق بـ`is_saas_admin`)؛ اختُبرت بمحاكاة Cloudflare. **غير منشورة** حتى توجد الأسرار.
- **لوحة المزوّد (`saas/domains-ui.js` + أزرار في `saas/app.js`):** في طلبات «ربط دومين خاص»/«DNS جاهز» زرّان جديدان: «ربط تلقائي بالشهادة» (يستدعي دالة `domains` بجلسة المدير، ويرسل للزبون نص السجلات المطلوبة: CNAME وTXT إن لزم وتنبيه الجذر apex) و«فحص الشهادة» (عند اكتمالها يردّ على الزبون ويغلق الطلب). النصوص الموجّهة للزبون بلا أسماء مزوّدين. اختُبرت منطقياً (Node: الاتصال بالدالة، الأخطاء، صياغة الرسائل) وتحميل الصفحة بلا أخطاء؛ **لم تُجرَّب مع Cloudflare حقيقية** (تحتاج الأسرار والدومين).
- بطاقة جهة الزبون (عرض حالة الدومين والشهادة في «إعدادات الموقع»): لم تُبنَ بعد، تأتي بعد ثبوت الربط الفعلي.

## 12) دراسة الاستضافة المقارنة (تقرير 10/10/2026، مرفق صاحب المتجر) — خلاصتها المعتمدة
- **التوصية:** Cloudflare Workers + Cloudflare for SaaS (Custom Hostnames) + Supabase؛ **واجهة مشتركة متعددة المستأجرين تحدّد المتجر من الـHostname** لا مستودع/مشروع لكل متجر (وهذا ما يفعله الموزّع في `saas/worker`، والمرحلة 4 تنقل المحتوى من المستودعات).
- **التكلفة (افتراض نطاق واحد لكل متجر، تشمل رسم النطاقات وWorkers الأساسي فقط، لا Supabase ولا شراء النطاقات):** 50 متجراً ≈ 5$/شهر، 500 ≈ 45$، 5000 ≈ 495$. **نطاقان لكل متجر (مع www) يضاعفان العدد**: 5$ / 95$ / 995$. حصة 100 نطاق مجاناً ثم 0.10$ لكل نطاق (سبق التحقق منها من صفحة الخطط).
- **Hostinger VPS:** ميزانية افتراضية 10–50$ لخادم واحد وليس عرض سعر؛ صيانة عالية ونقطة فشل واحدة؛ يُقارَن عند 5000 متجر بتكلفة خوادم متعددة + موازن + نسخ احتياطي. **Hostinger المشتركة وVercel:** غير موصى بهما كطبقة رئيسية (حدود غير محسومة/تسعير لا يتحمل آلاف النطاقات).
- **ملاحظات تصميم:** (1) لا يُكشف رمز Cloudflare API للمتصفح أبداً (متحقَّق: يعمل فقط في دالة `domains`). (2) لا تُعد العميل بزمن ثابت لإصدار الشهادة؛ تتابع المنصة الحالة (`cf_status`/`ssl_status`) وتعرض تعليمات DNS. (3) **النطاق الجذري (apex)** قد يحتاج إعداداً إضافياً (CNAME flattening/ALIAS لدى مزود الزبون): لا تفترض أنه يعمل بسجل CNAME وحده، والأسهل توجيه `www` ثم تحويل الجذر. (4) **عزل المستأجرين:** لا تُخزَّن مؤقتاً ردود الدفع/الحسابات/الطلبات تخزيناً عاماً مشتركاً بين المتاجر؛ مفتاح الكاش في الموزّع هو عنوان المصدر ولا يخلط مستأجرين مختلفين، وتبقى بيانات Supabase بسياسات وصول لكل متجر.
- **الدومينات:** شراء `.com` وغيره عبر API ممكن لدى بعض المسجلين (Cloudflare Registrar API تبدو الأنسب، تُتحقق صلاحياتها)؛ **`.dz` لا API عام موثق مؤكد** فيبقى مساراً بمساعدة المنصة أو مسجل معتمد.
- **لم يُتحقق منه بعد (يُختبر عملياً):** الأداء من الجزائر (قياس DNS/TLS/TTFB وزمن Supabase من الجزائر العاصمة والبليدة ووهران، ثابت وجوال)، وقبول بطاقة/PayPal صاحب المتجر في Cloudflare **باختبار دفع أول ثم تجديد تلقائي**، وحدود وشروط الاستخدام التجاري لخطة Workers عند آلاف النطاقات، والفرق بين Pages وWorkers وCustom Hostnames في الحدود.

## 13) مرحلة تجريبية بدومين مؤقت باسم أليسوم، ثم الانتقال لاحقاً (قرار 10/10/2026)
- **الفكرة:** نبدأ بدومين منصة رخيص باسم أليسوم (متاح وقت الفحص على `.com/.app/.dev`: `alyssumhub` و`alyssumcloud` و`getalyssum` و`alyssumapp` و`alyssumplatform` و`alyssumstores` و`alyssumshop` و`alyssumsaas`؛ `alyssum.com` محجوز) لتجربة الموزّع والشهادات والربط، ثم ننتقل لاسم المنصة النهائي. **لا يُستعمل `alyssumdz.com` ولا نطاق فرعي منه** (Cloudflare for SaaS يتطلب منطقة كاملة؛ إعداد النطاق الفرعي لمنطقة قائمة ميزة Enterprise).
- **ما يرتبط بالدومين (والتعامل مع تغييره):**
  1. إعداد واحد `PLATFORM_DOMAIN` في الموزّع، ويقبل الآن **عدة دومينات** مفصولة بفواصل: الانتقال = إضافة الجديد بجانب القديم ثم حذف القديم لاحقاً دون انقطاع.
  2. عناوين الزبائن `اسم.دومين-المنصة`: الاسم الفرعي محفوظ كتسمية (`saas_sites.sub`) فتعمل تحت أي دومين منصة؛ يُنصح بإبقاء الدومين القديم مسجَّلاً (≈10$/سنة) كي لا تنقطع روابط قديمة.
  3. **الأثقل: دومينات الزبائن المخصّصة.** الـCustom Hostnames مربوطة بالمنطقة (zone) التي أُنشئت فيها، وسجل CNAME عند الزبون يشير إلى `service.<دومين-المنصة>`. التبديل لاحقاً يعني إعادة إنشاء الـhostnames في المنطقة الجديدة (قابلة للأتمتة بالدالة `domains`) وطلب تغيير CNAME من الزبائن، أو إبقاء المنطقة القديمة حيّة. **لذلك الانتقال رخيص وقت وجود عشرات الزبائن لا آلافهم؛ ويُفضَّل الحسم قبل جلب زبائن بدومينات خاصة بأعداد كبيرة.**
